# PA 任务协调器模块设计与分期验收

本分支包含 P1–P6 的实现。P6 接入本人 QQ 私聊，使用隔离的本机模型和 QQ 接口验证实际程序路径。线上账号、供应商和部署状态需单独验收。

## P1 的运行与边界

`node scripts/verify-pa-tasks.mjs run P1` 从临时空库启动受认证的本机服务，执行 V01、V02。可用 `node scripts/verify-pa-tasks.mjs plan P1` 查看判据。P1 支持接单、按来源查回、状态查询和基于预期版本的续办。结案是协调器内部事务；自动通知目前以待投递记录保存。

独立服务编译后使用 `node dist/task-coordinator/main.js <私有数据目录> <socket或命名管道> <配置的owner> <凭证文件绝对路径>`。Unix 数据目录和 socket 父目录需要由运行账号持有且仅该账号可访问。凭证文件存储 32 至 256 字节的可见 ASCII 随机令牌，在 Unix 上同样限制为运行账号私有。用 Bearer 凭证对本机端点发送 `POST`，请求为 UTF-8 JSON，包含 `protocolVersion: 1`。部署端负责从真实渠道身份生成来源键和材料引用；请求体不能指定身份。P1 不启动 QQ、模型或执行器。

| 端点 | 请求体中除协议版本外的字段 |
|---|---|
| `/v1/submit` | `sourceKey` 和 `spec`，含 goal、capability、materials、deadlineAt（Unix 毫秒）、budget |
| `/v1/lookup` | `sourceKey` |
| `/v1/status` | `taskId`，可选 revision |
| `/v1/revise` | `sourceKey`、taskId、expectedRevision、newGoal |

任务完成后可基于指定版本续办。P1 的续办沿用原材料、预算声明和绝对期限。来源键必须在绑定身份内稳定标识渠道、消息和操作；旧回执重放返回原版本。独立协调库有应用标记和 schema 版本，不能把 PA 聊天库用作该数据库。

## P2 的运行与边界

运行 `node scripts/verify-pa-tasks.mjs run P2` 验证 V03 及接单回执超时。`WorkerRegistry` 登记协议、能力、格式、权限、实例名额和共享资源需求；`WorkerEndpoint` 从受信任的尝试存储端口读出分配结果，在记录“可能已发送”后才调用适配器。每个 worker 用独立凭证建立回报身份；回报还需匹配尝试、令牌及租约代次。接单超时记为未知，重复 start 不会再次调适配器。

P2 的测试用两个可控适配器和内存尝试存储验证调用边界。跨进程持久领取与占用记账归 P3，断电后核对归 P4。

## P3 的运行与边界

`node scripts/verify-pa-tasks.mjs run P3` 验证 V04、V05。为 `TaskScheduler` 配置账本、注册表、worker 连接凭证、全局名额和资源池上限；可设置每位发起人的并发数与每轮考察数量。把该调度器交给 `startCoordinator` 即可随服务运行。未配置适配器的独立启动命令只接单。

SQLite 保存领取尝试、执行令牌、工作区及资源占用。两个独立进程可以共享同一专用数据库和同一套容量设置。适配器调用在领取事务提交之后，返回不明时仍保留占用。需求可以绑定明确的前置修订，显式工作区键按所属人隔离。已接单任务的超期结论及未知占用核对属于 P4。

## P4 的运行与边界

使用 `node scripts/verify-pa-tasks.mjs run P4` 验收派发断点、执行方失联、取消与依赖收尾。恢复程序读取原数据库中的尝试键、派发标记和截止时间。确定未发送时可按原尝试派发；可能已发送时先查询原执行者，回执未知不会自动重新启动收费工作。

任务结论和物理名额分开记录。超过核对期限时可以向用户提供“结果未确认”的结论，但只要原执行还可能运行，就继续保留相应名额与工作区占用。确认停止后再释放，重复证据不会释放两次。迟到的可信结果追加在原尝试上；已发给用户的结论按原修订保留。独立池有余量时可继续接单。

通过认证的 PA 端点发送 `POST /v1/cancel`，请求字段为 protocolVersion、taskId、revision。尚未派发的任务可以直接取消；已派发的任务先登记意图。执行方只报告“已结束”时，协调器可以释放经确认的占用，但不能由此断定取消成功。补充等待中的材料时，调用 `/v1/revise` 并提供材料和期望修订；可为新修订显式指定新的绝对期限。原修订和原尝试的期限保留。

P4 恢复循环由配置了调度器的服务启动。只接单的独立入口没有外部执行方。Unix 服务异常退出后如遗留 socket，须由宿主在确认旧进程停止后恢复端点，服务不会删除仍可能在用的 socket。离线验收区分任务库重开和真实宿主守护进程重启。

## P5 的运行与边界

**QQ 用户入口。** 本阶段提供协调器后台能力。真实 QQ 上的派单、通知与领取由 P6 接线后另行验收。

后台按任务号及修订保存实际文件。暂存时核对执行身份、文件大小和 SHA-256；结案时再次校验并把产物引用、结论和待发通知一次提交。未提交的文件对收件人不可见，承诺交付的文件缺失或损坏时，返回真实完成情况。用户主动重领时，按原修订取出已保存的字节。

发送端先按真实来源确认目标会话，在发送每段前复核授权。每段预约后才调用传输接口。若发送后崩溃且送达无法确认，保留这一段的未知状态并停止本次剩余投递；同一会话的下一份通知可以继续发送。重复的同一条重领请求复用已有投递。

认证服务提供四个 POST 入口，均校验 protocolVersion 和当前所有者。`/v1/result` 按 taskId、revision 列出结论及文件；`/v1/artifact` 按同一修订和 reference 读取字节；`/v1/reclaim` 用真实请求 sourceKey 为同一修订创建投递；`/v1/delivery` 按 notificationId 查询分段回执。通用工作区、QQ 消息编号或同名文件都不能替代这些归属检查。

`outputFormats` 声明执行方需要支持的格式，`requiredArtifactFormats` 从中选择确实要交付文件的格式。未承诺文件的文字任务可以只返回结论。文件限制为每份 4 MiB、每次尝试合计 8 MiB，完整性检查覆盖摘要和受支持格式的标记或文本编码；不验证文档或图片的业务内容。暂存与历史成果占用数据库空间，本阶段没有自动清理期限。

独立启动入口可以查询结果和登记重领。实际投递需要配置绑定到渠道的投递适配器；仅开启查询端点不会发出 QQ 消息。

离线验收入口为 `node scripts/verify-pa-tasks.mjs run P5`，涵盖 V09、V10。结果可查与 QQ 实际接收分别验证。

## P6 的运行与切换

QQ 服务进程直接使用协调器的模块，任务、版本、交付文件、通知和工作名额保存在 PA 数据目录的 `task-coordinator.sqlite`。单机运行只需启动已有 QQ 服务。此模式共享进程生命周期，服务关闭期间停止调度。重启后按原尝试核对；已经发给模型的请求若查不到结果，会记为“结果未确认”，不自动重发。应保持 QQ 服务对该库的独占执行权。P1 的独立协调器服务仍可用于其他宿主和测试。已有独立 v4 库由写入端首次打开时升级至 v5。单独升级数据库不会切换 QQ 入口。若旧库的调度名额或资源池与 QQ 执行方不同，请保留原库与原配置。独立协调器的运行目录应与 PA 数据目录分开，两个宿主不得共用一个活动库。

在 `PA_TASK_COORDINATOR_ENABLED=true` 的实例中，唯一绑定的本人 QQ 私聊可提交和续办文字任务、查询、取消、重领。详见 [QQ 命令](../../README.md#本人-qq-私聊的后台文字任务)。执行方 `pa-text` 只生成文字，无工作目录、Shell 或项目写权限。并发上限为两次执行。自然语言由 PA 判断，明确的 `/task` 命令由程序解析。此次切换保留原 Codex 的数据库和请求编号；新功能关闭后，原任务的查询继续可用，执行和自动通知暂停，重新启用后按原状态处理。旧执行器独立运行，切换前应核对在途任务和未知发送，勿以新任务补跑。数据库和已保存的文件都需要保留。如果回退到没有切换逻辑的旧程序，应先停止接单并隔离旧写入入口，避免恢复旧投递。

本机管理员在编译后运行下列命令。数据库参数使用实际数据目录中的已有文件；命令以只读方式打开，允许的操作如下。

```sh
node dist/task-coordinator/operations.js <数据库路径> status
node dist/task-coordinator/operations.js <数据库路径> backlog
node dist/task-coordinator/operations.js <数据库路径> pools
node dist/task-coordinator/operations.js <数据库路径> inspect <任务编号>
```

`status` 显示各队列最老一项及名额，`backlog` 每类最多返回 32 条，`pools` 显示实际占用和仍待核对的名额，`inspect` 显示单个任务的最新版本及发送情况。输出省略任务正文和文件内容。离线验收使用 `node scripts/verify-pa-tasks.mjs run P6`。

## 一、关键决定

PA 负责理解用户并核验来源。通用任务由协调器统一接单、调度和结案。它提供独立服务入口，QQ 首版直接在现有 QQ 进程中启动协调器。每种 worker 通过适配器接入。模型每轮只提出所需能力、材料和完成条件；后台依据程序规则处理容量、授权、期限和外部回执。

首版选择单机 SQLite，协调器拥有独立数据库，P5 起交付文件随版本保存在该库，短写事务使用 `BEGIN IMMEDIATE`。把调度留给各 worker 也可以运行单项任务，但两个 worker 共用额度时，没有一个地方能同时核对剩余名额、工作区写权限和任务版本。统一事务可以完成这三项核对。单机是本次设计边界。多主跨机写入需要另行选型。

设计阶段的本地探针用两个连接检查了 SQLite 3.53.3 的基础行为。连接一持有写事务期间，连接二尝试领取得到 busy；连接一提交后，连接二按原状态领取影响零行。结论和通知在同一事务回滚后均不可见，提交后同时可见。这只支持事务选型，协调器的并发正确性仍须通过 P3。

## 二、模块与接口

以下路径均为实施时的建议归属。默认位于 `src/task-coordinator/`；现有 QQ、研究、提醒继续使用各自已确认的身份和数据契约。

| 模块 | 拟议文件 | 输入、输出与唯一职责 |
|---|---|---|
| 接单与权限 | `service.ts`、PA 端现有渠道接入 | 接收经认证的请求。来源、收件人和可选材料由 PA 按真实消息绑定。按稳定接单键查回，只向所属人返回编号或拒绝原因。初版沿用本人私聊权限。 |
| 状态与事务 | `store.ts`、`schema.ts` | 独占任务库的业务写入；核验期望版本、执行令牌，原子登记尝试、资源、结论及待发通知。状态转换只走这里。 |
| worker 契约 | `worker-contract.ts`、`registry.ts`、各自适配器 | 声明能力、输入输出、协议版本、权限、共享资源需求、幂等和取消能力。注册时验证冲突和必要字段。供应商凭证与调用细节由对应适配器持有。 |
| 并行调度 | `scheduler.ts` | 选取可以开始的修订，原子领取全部名额和工作区租约，提交后异步调用适配器。领取事务从不等待网络。 |
| 故障恢复 | `recovery.ts` | 独立处理每个到期项。启动时及定时按索引查到期记录；只读核对外部状态，执行到期结案、停止确认及资源释放。 |
| 产物与结案 | `artifacts.ts`、store 的结案事务 | 用协调器分配的任务/修订/尝试目录接收产物。校验大小、类型和摘要后冻结。按交付条件判定成功、部分完成或失败。 |
| 通知与运维 | `delivery.ts`、已有渠道发送队列、管理 CLI | 投递整份结果，记录每段是否送达；按任务和修订查询、授权重领，观测积压、过期及隔离资源。 |

### 跨进程协议 v1

同机用 Unix socket 与运行账号权限鉴别 PA、适配器和只读管理端；本地验收可用命名管道。请求内的自报身份不能替代连接身份。记录 `protocolVersion`；不兼容版本明确拒收。一次提交冻结输入引用和内容摘要，拒绝任意宿主路径及模型指定收件人。

首版采用分角色的本机端点。协调器为每个适配器绑定独立的可信连接身份，回报时要求“已认证的 worker ID = 此尝试分配的 worker ID”，并核验令牌。共用操作系统账号时，必须另配连接级身份认证；仅凭对同一 socket 的访问权限不足以区分不同执行者。管理端只开放查询，从管理角色发出的派单或回报请求直接拒绝。

| 操作 | 输入与返回 |
|---|---|
| `submit / lookupRequest` | PA 传来源消息及操作序号、目标、能力、交付条件、输入引用、期限、预算。成功返回 taskId、revision；相同键相同内容回原回执，不同内容返回 conflict。超时后使用原键查询。 |
| `status / revise / cancel / reclaim` | 程序按当前授权读取目标。续办传 expectedRevision、新要求和幂等键；取消区分已登记、已请求停止、确认停止。重领创建投递，引用原修订产物。 |
| `describe / start / inspect / stop` | 适配器登记元数据。start 传 attemptKey、执行令牌、输入、交付条件、预算和期限，返回 accepted / rejected / unknown 及可选外部编号。inspect、stop 不受支持时返回 unsupported，协调器据契约决定可用的恢复路径。 |
| `report` | worker 提交尝试键、令牌、单调事件序号及进度或结果；按尝试和序号去重。乱序进度不得倒退状态。终态含结论、证据、可领取产物；缺少必需产物的成功回报降为实际完成状态。迟到回报保留为补充证据。 |

### 持久记录

| 记录 | 主键/唯一约束与关键字段 |
|---|---|
| 请求、任务、修订 | 授权主体＋渠道来源事件＋操作序号唯一，保存请求摘要；任务有 owner、originRoute、headRevision；修订以 (taskId,revision) 唯一，保存能力、预期交付、固定输入、阶段、期限、预算、结论。 |
| 依赖与尝试 | 依赖精确关联上下游修订并记录是否允许部分结果。尝试记录稳定 attemptKey、worker、租约代次、最后进展、下次核对时间、发送状态、外部编号、效果是否已知。每修订最多一条有效执行权。 |
| 占用与工作区 | 每个尝试关联需要的全局、实例、供应商/硬件资源以及工作区。每单位占用有状态、数量、释放证据和时间。工作区一次只允许一个有效写者。 |
| 事件、产物、结论 | 唯一 (attemptKey,eventSeq)，保存事件摘要。产物按版本关联不可变位置与摘要；修订只允许一条原始结论，可信新信息追加。 |
| 通知与分段 | 唯一 (结论,真实收件人,投递目的)；目的区分自动通知与用户重领请求。逐段保存固定内容或引用、序号、状态与外部回执。 |

索引按访问路径设置：可调度修订按资源池、可用时间和入队顺序；待核对尝试按下次核对时间；依赖按前置修订；待通知按会话及时间。预算、队列上限和各阶段截止时间接单时冻结。所有时间用持久的绝对时间，重启后不重新发一份完整预算。任务正文与产物独立于队列扫描。

**三种状态分别存储。** 修订阶段取 `waiting_input / waiting_dependency / queued / running / reconciling / closed`；closed 附带唯一结论 `succeeded / partial / failed / cancelled / timed_out / dependency_failed / outcome_unknown`。尝试另记“尚未发送、可能已发送、已接收、已拒绝”，以及当前执行权和实际占用证据。通知持久化“待发、发送中、确认、拒绝或未知”。查询同时返回修订、结论及投递状态，管理查询可附带尝试和资源证据。

接单时明确拒绝发生在接单成功之前。已接单后不能再标成“没接过”。依赖满足后进入队列；缺资料的修订到等待期限后结案，用户补资料可以显式发新修订。成功结案、取消确认、到期结案都通过同一条件写入终态。某一尝试失去执行权后，只允许追加补充事实。资源占用有单独的唯一释放记录，重复停止证据不能重复释放。

## 三、失败与并发的裁决规则

**接单和派发的断点不同。** 本地接单成功意味着任务可查。在联系外部前，先通过事务把尝试从“尚未发送”改为“可能已发送”，然后才发请求。如果在标记之后、实际发出之前断电，恢复也按“可能已发送”处理。宁可本轮给出未知结论，也不凭猜测重复收费。仅当契约能证明从未执行，或属可安全重放的无副作用动作且预算允许时，才能按策略继续。普通的“暂时查不到”不足以证明没执行。

**终态与容量分别处置。** 排队时取消可立即结案；运行中先持久化取消请求，停止得到确认才记已取消。等待输入、依赖或队列都有期限。执行超时后，如旧执行是否停止尚不明确，进入有界核对；期满以“结果未确认”结束自动等待。迟到停止证据可以释放资源一次，但旧令牌不能再修改原始结论。没有新业务数据被覆盖，也没有隐式重跑。

**全局限制是硬上限。** 已确认运行和仍可能运行的尝试都占用其可能消耗的资源。仅看到心跳消失不足以释放名额。若本地进程已停但远端调用仍可能收费，可释放本机 CPU 占用，继续保留供应商和对应的并发占用。其他独立池在全局仍有空位时继续运行。需要故障期间保证独立业务可用时，为其预留名额；唯一资源已耗尽时按排队期限给出可查结果。

**领取和续办。** 同一事务复核依赖、预算、发起人配额、全局和共享池容量，再创建尝试并改状态。过期扫描结果用条件更新重新确认。不同发起人轮转，池内取最早可运行项，遍历采用持久游标和有界批量。针对同一旧版的两个续办用 expectedRevision 比较并更新，只有一个能成功。如果旧进程还可能改文件，新修订可以排队，但只能在确认旧写者已停或其写入能力已被隔离之后开始。首版允许事先声明的无环依赖；不依赖模型自动拆解任务。

**结案和通知。** 产物先写入暂存并校验；内容可读取后再把不可变引用、结论及通知意图一次提交。中断时按尝试键处理孤立暂存，未提交文件不能领取。QQ 消息在发送前持久预约，回执不明时停下这一次的剩余段，释放房间发送权。在同一会话中下一份通知仍可发送。用户明确重领时可再次发送整份结果，保留原投递记录，不调用 worker。管理端能区分“计算未完成”“产物已保存”“QQ 送达待确认”。

## 四、开发顺序与验收

批次依赖为 **P1 → P2 → P3 → P4**，**P5 从 P1 分出**，**P4、P5 汇合后进入 P6**。公共协议和存储由同一所有者维护；并行开发时 P5 通过已冻结的结案/通知接口工作，对共同 schema 的变更先在 P1 契约中协调。各阶段以对应提交和运行记录验收。详细动作、预期结果与证据在[唯一验收清单](task-coordinator-verification.json)，跨阶段引用同一编号。

| 批次 | 拟变更范围与交付物 | 阶段出口 |
|---|---|---|
| P1 接单与账本 | 服务入口、存储、权限、版本、状态转换和通知意图契约；用临时库启动和重启 | V01、V02。重送只产生一项工作，不同内容冲突，旧版续办竞争只有一个赢家，一版只有一条原始结论。 |
| P2 接入协议 | 能力目录、稳定接口、两个行为可控的适配器；一个能主动回报，另一个可以延迟或失联 | V03。新增适配器后经同一服务入口自动匹配；不具备权限或格式能力时没有外部动作。 |
| P3 调度 | 资源记录、调度循环、依赖查询和工作区独占；可独立启动第二个调度进程 | V04、V05。观测两个不同任务真实并行，同一任务不会双领；拥塞池不挡住有空位的池。 |
| P4 恢复 | 有期限的核对、取消、退避、依赖收尾、迟到事件和不明占用释放 | V06–V08。断电不会重开可能已收费的任务；一个 worker 失联时，其他健康池继续完工并接新单。 |
| P5 结果与通知 | 产物暂存与冻结、查询、通知分段、重领；接入原有渠道发送器 | V09、V10。损坏文件不能交为成功；送达未知时可查回原版，已记录的收费执行数不变。 |
| P6 集成、运维与切换 | PA 路由对接、只读管理命令、旧任务命名空间与单写入方切换方案 | V11、V12。旧数据可追溯、不误重跑；积压可定位，历史正文不会进入调度热路径。独立审查通过后才提出真实 worker 联调。 |

**验收取舍。** 每个 V 编号只有一个主要负责模块。存储约束在 P1 查账本，并行争领在 P3 用独立连接，P4 只补外部状态不明与断电次序，P5 只补真实交付边界。P6 复用前面已有剧本和断言，仅增加跨入口、切换和管理输出的观察。每阶段通过其服务入口或渠道入口取得回执，再对照数据库、实际文件或外部调用计数。单测适合纯校验；它不能独自证明接单、交付和恢复。

**性能验收。** 正确性门槛优先用可重复的计数：重复执行、跨版本覆盖和超额占用均为零；独立任务运行区间必须重叠。每次外部等待期间数据库读写必须能前进。P1 建立临时空库基线，P3 记录公平轮次、每轮扫描上限和实际名额，P6 与同机同数据的空载基线比较一万条旧记录时的查询计划和耗时分布。已有仓库没有通用协调器的耗时基线；部署机器的延迟目标与名额留到测量后定，不用臆造毫秒阈值。

**迁移边界。** 新请求由一个入口持有写权限；切换前检查旧队列、在途执行及投递状态，保存路由归属与原请求键。旧任务维持原账本的只读寻址。来源请求可能已由旧端接受时先核对，禁止在两边各派一次。回退时先停止新接单，让已有任务仍由其原协调器结案或提供只读查询；保留新旧数据和未知副作用记录。涉及真实供应商、QQ 或生产部署的验收另需授权。

## 五、CLI 和证据

当前可复用入口为 `node scripts/verify-pa-tasks.mjs`，用法及证据位置见[项目验收技能](../../.agents/skills/verify-pa-tasks/SKILL.md)。P1 从真实本机协调器端点验证接单和修订；通用调度、跨池并发和故障恢复仍是矩阵中的设计条件。已有 `repo-check` 继续承载编译和常规回归。

P1–P6 中需要反复调用的动作按阶段接入同一验证入口：选择场景、启动隔离服务、注入可控时钟或断点、读取结果与调用计数、输出证据。验证器独占其临时数据和测试 worker；故障注入接口仅由验证配置启用。运行中的用户任务不作为测试数据。P6 另外提供只读管理操作 `status`、`inspect <taskId>`、`backlog`、`pools`；用法见上文 P6 的运行与切换。
