# Companion Memory v1：确认方案与实施准备

历史决策记录：2026-10-16后续用户决定取消个人长期事件记忆和向量执行，只保留人物画像、群规则/共享记忆及房间Topic关键词检索。旧数据和版本保留，本文的个人事件、Embedding及四字段API为历史设计，以memory.md和最新用户决定为准。

日期：2026-10-13。状态：已按本方案完成本地实现与离线验证；真实模型质量、实际启用配置和 QQ mention 联调仍待完成。当前使用说明见 [memory.md](../memory.md)。

本文件整理用户逐项讨论后的决定，替代《companion_memory_system_v1_codex_spec (2).md》及 [v0.2 基线](pi_evolving_companion_technical_design_v0.2.md) 中冲突的记忆要求。原附件仅作设计来源，其末尾开发指令不构成额外操作授权。随后用户已明确授权实施。本文件保留决策与阶段规划，实际模块和验证边界见 [development.md](../development.md)。

## 1. 已确认的产品规则

| 项目 | 决定 |
|---|---|
| 技术路线 | TypeScript / Node.js，复用 Pi SDK；参考 Shiori 思路，不 Fork、不引入 Python |
| 人物身份 | 保留场景身份 actor_id，统一人物使用 person_id；确认属于同一人的身份关联到同一 person |
| 人物记忆 | 同一个人维护统一记忆与画像，按时间和归纳状态更新；私聊所得的人物信息可用于群聊，不再按群/私聊拆人物画像或可见投影 |
| 身份与权限 | 共享人物记忆不授予管理权限；昵称相同不代表同一人；原始消息仍保留房间、发言身份和时间 |
| 权威记录 | 数据库保存的原文为权威记录。自述、第三方说法和模型推断分别标记，不把所有陈述视为已证实事实 |
| 删除与撤回 | 不提供记忆删除操作；平台撤回不删除已保存内容，不联动清理 Topic、画像或索引；纠正通过新版本替代当前结论，保留旧记录 |
| 语义检索 | 只对 Topic 话题摘要生成向量并检索，不对人物片段或画像向量化，不增加人物 FTS/关键词补检链路 |
| 画像注入 | 只允许当前提问者和当前问题中真实 @ 的人物进入画像候选集；按 person_id 直接读取已有画像 |
| 群聊数量触发 | 每新增 50 条去重后的真人消息触发一批整理 |
| 私聊数量触发 | 每新增 50 轮完整问答触发压缩；一轮为一条用户提问及其正常完成的 Bot 回复 |
| 容量触发 | 数量阈值或最终请求上下文占用达到实际可用窗口的 85%，任一满足即可触发 |
| 并发 | 整理与聊天并行；同一房间整理任务按顺序提交，不同房间可并行；同一 Pi 对话会话保持单写入者 |
| 消费顺序 | 按入库顺序固定批次，不按发送日期跳选；迟到消息进入收到时的待处理队列 |
| 群摘要 | 首版不实现独立 room_summaries，不再增加常驻的群近况总结层 |
| 长回答卡片 | 合并转发式长回答展示延后，属于渠道发送能力，不作为记忆系统前置条件 |

原稿的“跨天按昨天筛选尾批”不进入本版调度。数量不足时仍可由 85% 容量线触发。人物画像跨场景使用的决定不等于复制其他房间全部原始聊天，也不自动开放任意历史导出；Topic 默认从当前房间检索，跨房间话题搜索不在本次确认范围。

## 2. 身份、来源与归纳产物

### 身份

保留现有 actors 与 rooms 的含义和主键。actors 表示房间内的发言身份；新增/扩展人物及绑定记录，使多个 actor 指向一个 person。rooms 继续使用 channel/account/room_type/external_chat_id 作为唯一组合。

已有 primary_person_bindings 迁移为通用绑定的来源，保留其明确 person_id。未绑定的成员先拥有独立人物记录；只有可靠的平台身份契约或明确绑定才能合并，不能根据名字、聊天内容或模型猜测合并。群成员 OpenID 与私聊 user_openid 的关联须有证据。ownerBindings 继续单独控制管理权限。

### 产物及来源

| 产物 | 用途与来源 |
|---|---|
| 原始消息 | 复用 messages，保留原文、场景 actor、room、平台事件 ID、发送/接收时间及稳定入库序号 |
| Topic | 一段具体讨论或事件，关联真实消息 ID；一批可产出多个或零个 Topic，一条消息可关联多个 Topic |
| 人物片段 | 对某人的自述、偏好或经历等证据，关联 person、Topic 和原始消息；归纳后仍保留，不设独立检索管线 |
| 人物画像 | person 当前已归纳的事实与偏好，保留修订、证据与有效时间；旧经历不因当前偏好改变而消失 |
| 私聊续聊摘要 | 压缩已处理的对话，保存讨论结论、决定和未完成事项；按 conversation 保存，不冒充人物画像 |
| 向量 | 只对应 Topic 的当前摘要版本；记录模型、维度、输入格式版本和内容 hash |
| 任务/检查点 | 批次成员、边界、状态、尝试次数、租约、来源版本及完成位置，支持重启恢复 |

私聊续聊摘要服务于本次对话连续性，与已取消的独立群摘要不同。群聊通过近期同房间消息、相关 Topic 和选定人物画像提供背景。群聊数量整理完成并不要求创建新的群摘要表。

自动提取必须区分“发言者”和“被描述的人”。Bot 已发出的回复可提供对话上下文，不能作为用户事实的独立证据。未发送或投递不确定的生成稿也不能写成共同发生过的经历。原文保留不等于所有原文始终进入模型。

## 3. 50 条 / 50 轮与 85% 的调度契约

### 固定批次与计数

入站先去重、入库，再分别通知对话队列与后台调度器；不能等待一次聊天模型请求结束后才接收后续群消息。

每个整理任务持久保存 room/conversation、触发原因、所选消息 ID 或完整轮次 ID、起止入库序号、输入版本和状态。正常数量批次取最早未占用的 50 条/轮；容量触发可以少于 50。数量不能由两个全局入库序号直接相减得到。

- 群聊计数只包括有效真人聊天消息；平台重放、Bot 回复、工具/系统事件不计入。管理命令是否作为整理上下文按其类型处理，不计入普通聊天阈值。
- 私聊按业务 run 的完整问答关系计数，不按 Pi 消息数除以二；失败、取消、纯管理运行不计一轮。未形成完整轮次的用户原文仍保留，并有显式处理归属，不能因完成水位推进而默默跳过。
- 已归属 queued/running 任务的消息不重复计入下一任务。正在整理 1–50 时，新到的 51 起归下一批；再次满额可排队。
- “任务已占用到哪里”和“已成功整理到哪里”分别记录。只有批次完整事务提交后才推进连续完成位置；失败保留原批次重试。
- 原始发送时间用于理解事件先后，入库序号用于稳定消费。积压、迟到、重启都不改变已固定的任务成员。

读取上一批少量原文作为背景时，将其标为只读来源，不重复计数、不重复产出同一事实。输入超出整理模型窗口时拆成有检查点的子任务；对原批次仍须有完整覆盖和明确成功条件。

### 上下文容量

设 C 为实际已配置且经验证的模型可用窗口，I 为最终请求输入 Token 估算，O 为预留的最大输出量，S 为估算误差余量：

```text
整理触发：新增数量达标 OR (I + O + S) / C >= 0.85
允许发送：I + O + S <= C，并满足供应商独立输入/输出限制
```

I 包括实际发送的系统提示词、角色/协议开销、可用工具描述、画像、Topic、续聊摘要、历史及当前输入。当前无工具仍需在统一请求构造处计数，避免以后加工具漏算。汉字数、消息条数和 Pi messageCount 均不能替代 Token 数；不能默认所有模型都有 1M 窗口。

先核对锁定 Pi SDK 的计数能力及所选模型的 tokenizer/估算方式。若不能精确计数，明确标识估算并留余量；真实接口返回超限时有限恢复并重新检查，不把估算宣传成绝对保证，也不无界重试收费请求。

同一输入水位已有任务时，85% 不重复创建任务。阈值检查也不因无新可压缩历史而反复触发相同整理。

### 并发及硬上限

聊天与整理用独立模型调用上下文；后台不能调用正在聊天的 Pi Session 的压缩/历史写接口。同一对话请求开始时固定所用记忆版本；整理结果提交后，下一次请求再读取新版本。

达到 85% 时可继续对话。若新请求在整理未完成时已超硬上限，该请求等待相关整理完成，重建最终请求并再次检查；等待应发生在数据库事务和人物/房间提交锁之外。后台失败需返回明确状态，不无限挂起。

如果超限主要来自当前单条输入或其他不可压缩部分，压缩旧历史也未必有效。实现阶段提供可诊断的过长输入结果，必要时显式分段；不静默裁掉原始用户问题，也不反复整理同一历史。

不同房间可并发，但共享同一 person 的画像更新必须串行提交或按版本 CAS 校验，冲突后重读再合并。任务还须校验当前租约所有者及输入版本，防止过期 worker 或旧结果覆盖新修订。LLM 等待期间不持有 SQLite 写事务。

## 4. 压缩、画像与检索

### 私聊连续性

未触发容量线时，前 50 轮使用完整历史。第 50 轮完成后固定批次并后台整理；期间继续用旧历史加新对话，但发送前遵守容量检查。

整理产物包括私聊续聊摘要、相关 Topic、人物片段与画像更新。下一次请求使用“已生效摘要 + 人物画像 + 相关 Topic + 未归纳的完整对话 + 当前消息”；当前消息只出现一次。不得把全部讨论内容压成性格/偏好，从而丢掉未完成事项。

压缩只更新模型活跃投影，保留 SQLite 原文及 Pi 审计记录。新摘要替换旧活跃摘要，不逐次堆叠全部旧摘要。续聊摘要须有完整来源范围；递归总结仍可沿来源关系回到原文。

### 群聊与人物画像

群聊按固定消息批次生成 Topic 与有价值的人物片段。画像按新旧证据更新，同一个人的跨群/私聊信息不做场景拆分。明确的用户纠正应立即影响当前画像，后台旧结果不能反向覆盖。

工程建议：首版在每个成功整理批次后，为确有新片段的人物安排增量画像更新，并使用 person 版本控制；不额外建设原稿的“每日/8片段”定时服务。该频率属于可调整实现默认，并非本次另行确认的产品阈值。

画像候选人物集合为：

```text
去重(当前发送者对应 person + 本条问题真实 @ 的其他 person)
```

从平台结构化 mention 信息获得身份，再做 actor → person 映射。普通文本里的名字、模型推断的人名、历史消息中的 @、@Bot 和 @全体不扩展人物集合；未知身份或无画像时不伪造内容。多次 @ 同一个人只注入一份。候选集内的画像按当前版本和上下文预算取用。

QQ 适配层需保留真实 @ 对象标识；harness 负责人物映射、去重和画像读取。已查代码只保留 mentioned 布尔值，真实 QQ 事件形状仍需一次针对性验收，不能把离线 fixture 当作实群证明。

### Topic-only 检索

仅 Topic 摘要做 Embedding，按相关性召回当前房间的话题及其来源引用。画像按上述人物 ID 读取；不额外检索人物片段、不建设人物 FTS、不过度扩展模型查询改写。人物片段保留用于画像归纳与审计，不能借 Topic 命中绕过两种画像注入条件增加其他人物档案。

只有向量版本、内容 hash 与当前 Topic 摘要一致时才参与语义检索。Embedding 可独立重试，不能因此重复提取 Topic。没有可用向量时返回明确状态，不把关键词结果或测试向量声称为真实语义召回。

首版可先采用不可变批次 Topic，保留来源关联；跨批改写/合并 Topic 属于后续优化，不以此扩大第一条纵向切片。相关人物细节是否能被 Topic 摘要覆盖由评测确认，不承诺所有细节必然命中。

## 6. 增量迁移与兼容

1. 新 schema 从当前 v5 增量迁移，迁移前做一致性备份，保留所有已有 message/run/delivery/actor/room/person ID 和关联；未知高版本拒绝自动改造。
2. 为既有消息回填稳定入库序号，保留原始时间；需要重建表时用事务迁移并核验外键，不重置数据库。历史消息能否自动回填记忆由单独 backfill 操作控制，首次上线默认不批量触发旧历史付费提炼；当前活跃请求因旧历史达到容量线时，可按固定容量批次压缩这些历史。
3. 既有绑定映射到通用 person；未验证身份不合并。已有显式记忆保留其来源与版本，不把 legacy 未知归属直接猜成某人的画像。
4. 本版移除删除操作，已有 deleted/tombstone 与已清空正文按历史状态保留，不尝试从审计/旧聊天自动恢复。此后纠正保留旧正文；“不喝咖啡了”可以更新当前状态，“忘掉/删除”不再触发擦除。
5. 上下文切换继续沿用 SQL 代次 → Pi 公开 API 持久化活跃投影 → SQL 确认的恢复协议。不得只替换 agent.state.messages，也不能直接打开 Pi 自动压缩而绕过当前摘要校验与审计契约。
6. 控制记忆使用与管理授权分离。新增的 @ 对象画像使用不自动赋予提问者修改他人档案、设置身份绑定或导出全部记录的权限。

## 7. 实施顺序与每步验收

| 阶段 | 可运行交付 | 主要验收 |
|---|---|---|
| M0 接口验证 | 确认 Pi 最终请求构造/Token 估算及独立调用方式；定义模型/Embedding 测试接口；验证 SQLite 向量候选方案 | 在临时环境验证，不修改生产配置；记录计数准确性边界和扩展兼容性 |
| M1 身份与入站 | 通用 person 绑定、mention 规范化、稳定顺序、先入库再派发；停止产品删除路径 | v5 数据无损迁移、重放去重、同人多 actor 共用记忆、不同人不误合并、撤回不删记录 |
| M2 后台纵向切片 | 固定 50 条/50 轮任务、持久租约、独立整理调用、Topic/片段落库；先用确定性模型响应 | 聊天不停、同房间批次有序、失败与重启恢复、过期任务拒绝提交、消息不漏不重 |
| M3 画像与压缩 | person 增量更新、私聊续聊摘要、两种画像候选条件、85% 触发、硬上限等待重建 | 私聊跨场景画像可用；未 @ 者不注入；摘要与画像不混淆；新旧请求版本不串；压缩后仍超限有明确结果 |
| M4 话题语义召回 | Topic Embedding Worker、同机持久化向量、摘要版本检查、受控真实模型评测 | 只有 Topic 向量化；人物无额外检索；中文语义查询用真实 Embedding 验证，故障不假报成功 |
| M5 集成与运维 | 当前状态文档、任务/积压/用量诊断、重试入口、备份恢复与完整回归 | 模拟渠道端到端通过，随后按授权进行 QQ/模型联调；列出尚未实测能力 |

开始实施时优先完成 M1–M2 的最小纵向切片；M0 中与向量有关的验证可在 M4 前完成，不阻塞无密钥的核心开发。无真实模型凭据时使用测试提供者验证契约，不声称已验证提取质量。独立测试适配器仅用于测试，不增加产品预览模式。

实现阶段的检查为 npm run check、npm test，并按阶段运行最窄的相关用例。代码非小型改动需要独立只读审查。文档准备后已进入实施；检查使用临时数据库和本地 HTTP，未调用真实模型或变更运行服务。

## 8. 必须覆盖的行为用例

| 类别 | 用例 |
|---|---|
| 数量 | 群第49条不触发、第50条一次、第100条两批；私聊失败回复不凑一轮，50个完整问答一次 |
| 快照 | 第一批模型暂停时收到新消息和新提问；旧批次成员不变、新消息计入下一批且提问可完成 |
| 幂等 | 单条消息重放、任务提交后重启不重复提取；失败不推进完成位置；旧租约结果不可提交 |
| 顺序 | 迟到消息按到达顺序处理；入库序号有空隙不影响计数；没有 Topic 的批次仍正常完成 |
| 并发 | 不同群可并行；同群整理按序；同一 person 跨群更新冲突不丢修订；等待后台时不持有其所需锁 |
| 容量 | 不足数量但完整请求达到85%也触发；已有任务不重复建；系统/画像/Topic/输出预留均计入 |
| 硬上限 | 后台未完成时请求超限会等待重建；后台失败有界返回；单条长输入和无可压缩历史不形成死循环 |
| 私聊 | 前50轮完整上下文；压缩保留未完成事项；原文不变；摘要加新历史不重复当前消息，重启后连续 |
| 身份 | 已绑定同人在私聊得知的偏好可供群聊使用；同名不同人不合并；owner 权限不随 person 共享扩张 |
| 画像 | 仅发送者与本条真实@对象；重复@去重；文字名字、@全体、历史@、未知ID不扩展候选 |
| 纠正 | 新自述纠正生效且旧记录保留；较早自动提案不能覆盖较新人工更新；模型回复不充当用户事实 |
| 留存 | 平台撤回后原文、记忆仍存在；所有产品删除入口移除；历史已删除正文不自动复原 |
| 向量 | 人物片段不请求Embedding或FTS；旧版本向量不能用于新Topic；向量失败不重复生成Topic |
| 质量 | Mock 检查结构与流程；另用真实模型检查人物归属、临时状态、语义召回和续聊连贯性，分别报告 |
