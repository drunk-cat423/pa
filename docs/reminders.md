# 一次性提醒：实现与验收

实现采用schema33，部署核对见[服务器部署](deployment.md#schema33一次性提醒)。范围仅为用户明确交代的一次性提醒，研究任务保持原流程，不根据画像/聊天背景自行创建任务。

## 实现

普通渠道对话在prepare_turn之后提供create_reminder、list_reminders、get_reminder、cancel_reminder。模型使用现有北京时间上下文解析相对时间；时间或事项缺失时只澄清缺失部分。本人当前轮明确承接紧邻澄清时，可以继承此前已说明的事项和候选时间；例如用户补充“八点吧”时不要求重发事项。已有“晚八点”候选时按晚八点理解；截止日期没有具体时刻仍需澄清，提醒时间也必须满足“之前”等界限。应用以当前真实来源消息ID和会话ID绑定人物、身份权限及原投递路由，模型无需重复摘录原文，也不能传owner、其他收件人或route。不得从画像、历史习惯、他人发言、引用或模型建议自主创建。语义识别仍需真实模型验收；程序不声称理解自然语言授权。

SQLite提交后，runtime使用程序生成的具体北京时间、事项及原会话回执确认，立即结束循环，不额外调用模型写确认。失败、已取消或已送达的幂等请求不伪造新安排；查询、取消按本人和场景授权，群只访问本群，私聊可以管理本人绑定私聊的提醒。

ReminderService随harness启动，立即检查一次，以后每秒检查到期索引。每轮最多处理20项、读取100个待通知候选，同时最多2个不同会话发送，同会话串行复用已有输出队列。后台不构造提示词、不调用模型。发送前在实际轮到输出时重新校验取消状态、绑定与允许场景，避免排队期间授权变化仍发出。

过期本地领取可以恢复；通知已经sending却没有确定回执时，过期后转uncertain，永不自动回queued。尚未尝试发送的到期项在恢复后发送一次；比原定时间晚至少60秒时，正文标明原定北京时间及“现补提醒一次”。正常平台网络延迟不属于毫秒级准时保证。

QQ使用主动文本消息。群@的标签使用官方`<qqbot-at-user id="..." />`格式，ID取原群发起人的member_openid（经现有actor保存），不拿私聊user_openid替代；正文中的平台@标签被转成普通文字，不能扩大收件人。官方文档确认群文本支持该标签，但没有明确说明该字段的身份域，原群ID映射仍需真实群验收：[QQ文本交互](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/trans/text-chain.html)。私聊不带@。

## 工具选择与时间格式

模型按用户委托的动作选择工具，不按时间或“调研”字样选类别：提醒本人去做→create_reminder；明确委托PA后台研究产出→create_research；普通问题当场答。普通待办、未来定时启动研究当前未支持，有歧义先澄清；“我的清单”缺少类别上下文时也先澄清。没有新增分类模型、研究定时执行或收费重试权限。

时间经过四层：本轮服务器时钟转换为Asia/Shanghai，并提供原currentMessage.sentAt作为相对日期依据；模型调用工具填写绝对remindAt和固定timezone；Pi按JSON Schema的字符串长度/ISO pattern校验，错误不进入执行器；存储再次检查日历日期、有效时间戳及首次创建是否在未来，随后以UTC毫秒保存。北京时间15:00+08:00与07:00Z表示同一时刻，程序确认统一显示北京时间。缺秒、缺时区、自然语言日期、2月30日或过去时间均不能创建新任务。

格式错误可以在现有模型/工具预算内返回参数错误供模型修正，不能静默猜测时间、扩充预算或假装已保存。格式合法不等于模型正确理解了用户意图，真实DeepSeek语义质量仍需获授权后测量。

边界语料：

| 输入 | 应有行为 |
| --- | --- |
| 明天下午三点提醒我调研DeepSeek-Bot | 只安排提醒，不执行研究 |
| 把DeepSeek-Bot加入研究清单，研究完告诉我 | 后台研究 |
| DeepSeek-Bot是什么 | 当场回答 |
| 把交电费加入任务清单 | 说明无通用待办入口，澄清是否需要定时提醒 |
| 明天下午三点开始帮我研究DeepSeek-Bot | 说明无定时研究能力，不擅自立即执行或改成提醒 |
| 明天帮我处理一下这个 | 澄清动作、对象和时间 |

本地固定响应只验证两种工具同时可用时的执行分流、澄清无副作用，以及错误格式修正后才进入执行器；不能把这组离线测试当成真实模型分类准确率。新增用例也复现并修复了旧承诺检查误拦“你希望现在研究，还是到时提醒你？”的问题，保留对明确未保存承诺的拦截。

## 成功清理

QQ返回成功和外部消息编号后，在同一事务中保存work_delivery_receipts，并移除这项提醒的work_items/authorizations/attempts/events/notifications行。原始聊天、Pi日志、画像、研究资料不动，不把提醒发送正文再次复制进聊天库。

回执只含编号、源消息/key、owner、输入哈希、结果、平台消息编号和到期时间，没有事项或通知正文；保留7天，每次最多清理100条过期回执。它用于阻止同一原始操作在清理后的短期内重复安排。原聊天本身仍保留原始请求，因此此功能不是全盘内容抹除。

发送结果未知、明确拒绝、取消或权限暂停的事项不按成功清理。确认已送达但写库失败时，事务回滚保留sending现场、停止服务；恢复为未知，不冒险重发。查询投影区分awaiting_delivery、sending、delivery_uncertain和delivery_rejected，不把通知生成完成误报为已送达。

## 验收标准与自动用例

| 验收点 | 操作及预期 |
| --- | --- |
| 保存后才确认 | 本地SSE依次返回prepare/create；确认发送前检查真实库已有1项提醒，仅2次模型请求，无第三次确认调用 |
| 失败/模糊不承诺 | 存储拒绝或参数缺失不能输出已安排；模糊时间走澄清、不建任务。模型措辞识别另列人工项 |
| 权限隔离 | Bob不能读/取消Alice任务；同人物群查询不泄私聊任务；身份重绑不转移旧事项 |
| 到期与重启 | 到期前不发送；关闭原harness后重新启动提醒服务，实际1秒循环发现逾期项并只发一次，原会话/发起人一致，模型请求数不增加 |
| 取消与未知结果 | 等待输出期间取消或撤销场景权限不发送；发送返回unknown，重开服务仍不重发，查询显示delivery_uncertain |
| 清理与幂等 | 成功后事项及待发正文不存在、原聊天仍在、无正文回执存在；同来源/key不能重排；清理写入失败全部回滚 |
| 分页与恢复 | 超过100项后仍能分页查到并取消旧任务；queued通知跨重启可发现，sending/uncertain不重新领取 |
| QQ协议 | 捕获主动消息POST，确认无被动msg_id、群标签目标来自受控sender、正文不能注入@全体、私聊没有群@ |
| 升级 | schema31/32升级33保留原文及已有提醒，旧库备份、外键与研究清理契约正常 |
