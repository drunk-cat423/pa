# 2026-10-23 故障修复与健壮性审查

依据当天生产失败记录和独立代码审查，检查了前台 Pi 循环、QQ 投递、后台研究、资料整理、压缩、SQLite/Pi 恢复以及人物授权边界。下表记录可定位的触发条件与处理结果，不代表所有网络或模型行为已经穷举验证。

| 已确认问题 | 修复与保留的约束 |
|---|---|
| prepare_turn 把群事实专用字段放入AI画像，整个问题无法回答 | 参数/业务拒绝作为工具错误回传，在原次数内修正；成功准备前仍禁止其他工具和正式回答 |
| 保存片段仅8000码点却请求offset=14000，整批研究立即失败 | 返回正文总量、有效范围及下一未读位置，允许有界修正；网络未知、取消和存储错误不当成普通参数错误 |
| 无保存回执却说“记下了”，整条回答静默丢失 | 余预算内最多重写一次并禁用工具；不能修正则形成明确未保存的程序回执，并保持Pi/SQL回答一致 |
| 同批研究A已保存，B出错后A的确认也丢失 | 保留逐项成功回执，修正B不重跑A；纠错请求超时仍报告已保存的标题/编号，其余未确认 |
| 超时、预算或前置容量失败没有用户可见回执 | schema28保存独立任务失败投递。先预约再发，只有sent才进入历史；任务/run仍失败，未知投递不重发 |
| 两房间同时对同一个人的画像捕获同一版本，提交冲突毒住资料FIFO | 同一数据库的materials任务逐项公平串行，跨进程检查有效租约；压缩独立，等待可取消，阻挡时等巡检、不忙轮询，保留CAS |
| 已纠正旧消息在压缩水位之前，导致之后所有摘要一直隐藏 | 压缩输入带程序确认的纠正链，提交冻结快照里的纠正指纹。覆盖对应纠正后恢复可见；在途新纠正、旧无指纹快照仍按未覆盖处理 |
| 多个schema拒绝工具结果把计数推过checkpoint上限 | 工具预算消耗封顶，跳过未执行操作不虚耗额度；原错误仍留在Pi/诊断，不因拒绝次数多而伪装数据库损坏 |
