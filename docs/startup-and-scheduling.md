# 启动核对与渠道调度

2026-10-26，schema31。通用逻辑仍位于 harness，QQ 只提交消息并执行投递。

## 启动

过去每次启动都会枚举历史任务、读取所有独立 Pi JSONL，再加载全部关联 SQL 消息。现在为每个独立任务会话保存完整性 checkpoint：状态、修订号、Pi 文件 SHA-256、SQL 关联摘要和核对时间。

首次升级把旧任务登记为 dirty，仍需要完整核对一次，不把未经验证的历史直接标成可信。后续启动仅读取 dirty 和未完成任务；已核对历史不逐个 stat/read。主 CLI 会话仍按原方式读取，其 SQL 关联使用独立索引，避免为了找到少数主会话消息扫描全部任务历史。

正常 SQLite DML 会通过触发器标记相关任务 dirty，修改归属同时保留 OLD/NEW 痕迹，删除关联也不能删除核对账本。成功回复保存后重新读取实际 JSONL，核对运行标记、输入、输出和 SQL 关联；只有修订号未变化才提交 checkpoint。持久化失败不能靠内存中的回复冒充成功。

每60秒巡检一个历史文件，持久记录轮巡位置；本地维护可用 `RecordedConversation.auditSessions({full:true})` 做完整核验。离线文件修改可能延迟到巡检才发现，不能宣称和每次全量核对有同样的即时保证。以这个默认速度，N个历史会话完整轮巡约需N分钟；这是低后台I/O配置，不是完整性实时监控。

确认损坏的任务房间停止新执行并关闭该房间的后台整理，其他正常房间继续使用。真正的数据库持久化错误立即通知服务停止。原文、旧 Pi 文件和审计保留，未知模型请求不重试，未知投递不重发。

维修须先停服务或取得对应会话锁，恢复正确原始文件/SQL；随后由本地操作者通过 `SessionIntegrity.audit({full:true,recheckCorrupt:true})` 重核。已有文件及 SQL 哈希仍必须匹配，不能清空哈希或把 corrupt 直接改成 verified。重核通过后重启房间。这个接口没有开放给聊天工具。

## 队列和慢投递

原文和需要回应的 channel_task 同事务保存。生产 QQ 入口收到 `accepted` 只表示已持久排队，不能显示为回答已送达；任务最终结果经回调更新状态。

等待任务正文留在 SQLite，调度按允许房间轮转，每次只用有索引的 `LIMIT 1` 领取一条。同一房间最多有一项未投递完的前台任务。上一条最终回答发送慢时，该房间后续问题继续留在库里，不预先计算大量回答；全局模型计算槽在计算完成时释放，其他房间仍能回答。研究通知等正在使用该房间输出队列时，也暂缓该房间的新领取。

关闭或完整性核验失败发生在领取后、创建 agent_run 前时，只能将这个确定未开始的本地领取退回 queued。`beginRun` 与任务 running 状态同事务；有 run 的任务可能已产生费用或控制操作，不能走这条退回路径。进程崩溃后也按相同边界恢复，保留未知请求状态。

恢复只查询 running 索引，不加载所有 queued 的正文。schema31一次修正旧 queued 却已有 run 的不一致状态，保留原任务和原文。正常新流程不产生这种组合。

仍有两项明确限制：

- 图片下载/准备发生在原文入库前，仍使用房间内串行 admission；本轮没有改成附件持久准备队列。极端图片洪峰的入口内存不是完全有界。
- 内部测试和CLI调用可选择等待最终结果，`handle()`默认兼容这种方式，保留 taskId→resolver；生产QQ显式 `waitForResult:false`，不积累整个等待队列的Promise。工具循环内的进度或文件投递仍需等待真实回执，不能把这些提前算作发送成功。

## 离线性能与回归

在本机 Node24/SQLite、100,000条任务会话登记及100,000条排队任务的合成数据上：

| 操作 | 原方式 | 新方式 |
| --- | --- | --- |
| 历史会话登记读取 | 全量100,000行，约171ms | dirty查询无新增，约0.75ms |
| 未完成运行查询 | 扫描历史约32ms | 部分索引约0.11ms |
| 队列恢复 | 扫描queued约191ms | 只查running约0.19ms |
| 任务正文载入 | 全量100,000条约1362ms、JS堆增量约360MB | 领取1条约4.9ms、JS堆增量约9KB |

这里比较的是移除的全量操作与新的有界操作，不能把它解读成整机吞吐倍数。SQL规模实验的verified登记是合成数据，没有伪造“十万个真实文件已核验”的结论；真实JSONL的首次核对、二次启动零历史文件read/stat、篡改、删除关联、损坏房间隔离、CAS、恢复不重发分别有实际临时文件回归。

证据保存在本地 `.local/long-task-20261026/`。工作台账的设计、复核结论和独立索引原型见 [work-ledger.md](design/work-ledger.md)。
