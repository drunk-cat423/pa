# GitHub Trending 群日报

每天北京时间08:50向显式配置的现有QQ群发送一篇日报，包含日榜最多5项、周榜最多3项、月榜最多2项。依据GitHub官方全语言Trending页面的排行顺序选择，跨分组去重并向后补位；当真实榜单去重后不足时显示实际数量，不编造补足。日/周/月是GitHub榜单的统计周期，并非PA自己统计的自然日历榜。

8:45开始采集三个官方榜单，选出项目后按“简介优先”准备资料：`description.trim()`非空就只用榜单简介及语言；仅简介为空或全空白时读取仓库实际渲染的README正文。不会为有简介的项目额外下载README，也不把已有无关README送入模型。当前模型据此概括用途、主要特点和适用场景，资料短时不为凑字数猜测。

README通过既有`fetchWebDocument`读取公开GitHub仓库主页，只取README正文，不把导航、About、脚本当作README，也不猜固定文件名或默认分支。仅对需要补充的入选项目并发读取，最多2路；每项正文最多8000字符，保留来源URL、抓取时间、状态和截断标记，沿用现有代理、公开地址、超时及响应大小边界。已成功冻结的正文复用；缺失、读取失败或旧快照没有README时如实标记，不能声称已读。旧榜单原始快照不会被就地改写；可显式调用`enrichTrendingReadmes`获得副本后预览。

使用Pi的Tool参数schema和`validateToolCall`：本期仓库slug是必填属性，每项值为AI总结，强制调用唯一提交工具。仓库名称、分组、顺序和链接始终由真实榜单决定，模型不能新增项目或URL。所有网页资料只作为资料，不执行其中的安装命令、角色要求或工具指令；不依赖浏览器登录、GitHub密钥或新的生产依赖。

每个项目必须有真实AI总结，原始描述和程序固定模板不能替代。当前百炼DeepSeek端点不支持`response_format: json_schema`，但已真实验证Pi的schema工具调用可用；strict参数、强制工具选择、本地校验和有界修复共同使用，不仅依赖“输出JSON”的提示。保留合格项目，缺项、占位或无实际总结时把具体错误交回模型，只修复未完成项。归一化空白和无害格式、按UTF-8预算限长，保持项目名和链接完整；没有资料时由模型如实说明信息不足，不让程序伪造用途。JSON Object与Schema的差别见[百炼官方说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。

08:50开始主动Markdown投递，日/周/月分别组织消息，遵守原有每段1500字节限制，整篇最多5段。项目名称、简介和链接作为完整段落一起发送，不拆出只有链接的尾段。同群复用完整回答输出队列，逐段保存平台回执。正常网络和QQ排队可能造成秒级延迟；8:50至9:50前启动会补发今天一份，晚于原定时间至少一分钟会标注补发，不连续补历史日期。采集、发送、补发截止和展示共用`src/trending-schedule.ts`中的时间定义。

## 开启与范围

```dotenv
PA_TRENDING_ENABLED=true
PA_TRENDING_GROUP_IDS=已在PA_QQ_ALLOWED_GROUPS中的group_openid
```

默认关闭。开启时必须显式填写已有QQ群的非空子集，不能填写私聊ID；新增QQ允许群不会自动订阅日报。当前模型、网页读取和代理沿用PA配置。定时器由QQ已就绪后的ChannelHarness启动，服务关闭时取消采集和模型等待，并等待已开始的投递确认。

## 状态与恢复

`PA_DATA_DIR/trending.sqlite`独立保存每期榜单快照、生成正文、冻结目标群和逐段状态；现有整目录备份自动覆盖。日报不注入个人画像或真人聊天历史，也不创建个人研究任务。

- 正式期按北京时间日期幂等；重启复用已生成正文，已发送段不重复发送。
- 采集失败最多尝试3次、间隔60秒，不使用旧榜单冒充今天；当日失败不阻塞下一天。
- 正常成功只需一次模型调用，初始生成与修复合计最多3次。`generation`持久保存已通过总结、已用次数和允许上限；发起调用前先记次数，重启不会重置预算。只有全部项目都有AI总结才准备投递，耗尽仍未完成则明确保留生成失败及已有结果，不发送原文版，也不阻塞下一期。
- 外部取消仍停止当前工作，本地诊断或数据库持久化故障仍按fatal处理。生成超时须先等待清理结算，最多额外等待1秒；仍未结算时保留生成未知、不投递，晚到持久化错误仍通知harness。
- 服务崩溃等遗留生成失败可显式申请恢复：只允许当天正式期、已有榜单快照且从未创建任何投递分段的记录。复用原快照、原目标群和已通过的AI总结，首次恢复请求追加一次最多3次的模型预算；同一请求重复执行不再次加预算。原失败信息保留，不另建QQ连接。显式恢复可在9:50后补当天，次日不追发。
- 明确拒绝或投递未知时停止该群余下段落，不自动重发；其他群独立处理。
- 普通采集/模型/平台失败记录为日报功能失败；真实本地持久化故障按PA原有规则停止服务，不能伪装为普通网络错误。

`harness.info().trending`展示功能状态和下次发送时间；完整每期状态与分段回执由下面的终端入口查看。

## 操作者验收

```bash
# 在发布目录，由有权限读取生产环境文件的操作者执行。
node --env-file=/etc/pa/pa.env dist/trending-cli.js preview
node --env-file=/etc/pa/pa.env dist/trending-cli.js request-test test-20261030
node --env-file=/etc/pa/pa.env dist/trending-cli.js status test-20261030
node --env-file=/etc/pa/pa.env dist/trending-cli.js status
node --env-file=/etc/pa/pa.env dist/trending-cli.js recover YYYY-MM-DD
node --env-file=/etc/pa/pa.env dist/trending-cli.js request-ai YYYY-MM-DD
```

`preview`会采集并调用真实模型，仅向终端输出`{parts}`，不创建`TrendingStore`或发送任务。预览与正式发送共用纯函数`formatTrendingParts`，按真实1500字节/最多5段规则检验标题、分组、项目段落和链接；得到可投递分段不代表已经送达QQ。

复演已保存的当天榜单时，可在独立数据目录依次调用`enrichTrendingReadmes`、`generateTrendingDigest`和`formatTrendingParts`，保留原项目和排序并记录实际资料来源；不要为了“只预览”运行`request-test`、`request-ai`或`recover`。`request-test`会写入独立手工期，由正在运行的PA服务生成和发送，不建立第二个QQ连接，不占用当天8:50的正式期。同一测试编号不会重复创建；重新付费测试须明确使用新编号。入口不开放为聊天工具。

`recover`是已授权操作者的显式恢复操作，不是状态查询；日期必须是北京时间当天。它仅持久排队，实际发送仍由运行中的服务执行。已投递、投递未知或已拒绝的分段不能借此重发；同一恢复请求和服务重启不创建新的日报期。生产使用有权限的操作者载入环境，再以PA服务用户执行，避免生成root所有的数据库附属文件。

`request-ai`仅用于给当天已经投递的旧版原文降级日报补充AI总结：继承该期原快照和原目标群，创建固定编号的独立补充期，标题明确标为“AI总结补充”，不修改原已发送分段。它会调用模型，按同一生成与修复预算处理；重复命令和重启不会创建第二份补充期，次日不自动追发。普通日报失败不能借此绕过`recover`的未投递校验。

离线检查：`node scripts/repo-check.mjs trending`。现有两组集中回归覆盖真实Pi到本地HTTP的生成协议、真实SQLite的到点/重启/关闭/失败恢复和逐段投递；真实榜单、模型简介质量以及QQ送达需实际验收，不能用Mock成功代替。
