# 记忆系统 v1

当前实现为 TypeScript / Pi SDK / Node 内置 SQLite。开发约定见根目录 [AGENTS.md](../AGENTS.md)，本页说明当前行为；[逐项确认方案](design/companion_memory_v1.md)保留设计背景。示例配置默认关闭后台，实际启用及模型预算由操作者配置；离线验证不能代替真实模型语义和QQ客户端验收。

## 画像归纳与回答时的使用

即时`prepare_turn`与后台整理共用`src/profile-policy.ts`。个人画像只收录对象明确、具体、稳定且对未来回应有用的本人特征、长期背景和互动偏好；一次提问或观点不自动证明稳定兴趣。任务指令、临时工具配置、一次性事件、玩笑、模糊指代及对AI的设定不写成个人特征。明确长期要求“技术方案不可行时直接指出”是互动偏好，“帮我调研这个链接”是研究任务。人物内部仍只有已归档和未归档，不新增分类。

人物和AI的待整理正文允许归纳，不要求连续摘录。当前真人明确确认紧邻、对象清楚的保存提议时，可保存被确认的归纳内容，仍绑定当前确认消息；旧历史或AI提议本身不授予保存权限。新本人pending不复制原话证据；第三方仅保留真实对象定位token，仍核验管理员与真实@/明确身份。成功更新只保留来源关联及必要对象元数据，不额外复制原话段落。原始聊天、旧版本、旧证据及固定输入按原规则保留，已冻结旧任务不静默改协议。

AI全局画像可以记录“何为生命第一因”这类长期关注课题，沿用现有全局画像位置跨群/私聊注入，不建独立模块。课题属于AI而非发起者；相关时使用，不强行带进每次回答，也不代表已创建后台研究或空闲自动思考。真实文件调研仍须通过研究工具创建任务。

Topic继续按房间自动FTS5/BM25检索，但只提供辅助背景，不能决定本轮对象或取代当前问题、紧邻问答及经核验原始资料。相同术语不代表相同项目。人物画像只用于当前相关的交流偏好/背景，不让泛化兴趣覆盖明确问题；上述规则不新增分类模型调用，不重排固定摘要与增量历史前缀。

既有污染不会因提示词修改自动消失。本地操作者可先审阅完整当前revision，再调用`autoMemory.reviewProfile(personId, expectedVersion, retainedFactIndexes, rewrites?)`保留指定旧事实，按需归纳这些旧事实，生成新revision；不得从已移除索引创建新事实。保留原顺序、来源类型、原始时间及补充确认关联，版本变化、存在queued/running资料任务或尚待自动恢复的失败资料任务时拒绝。该方法不注册为聊天工具，也不直接修改Topic、AI画像或研究任务。操作前备份，保留私人审阅清单；不把生产画像写进仓库。原文并未删除，日后人工重开已耗尽的历史任务属于新的操作，需重新检查其画像影响；这里不承诺模型永远不会再次误收。

`autoMemory.selfProfile.review(expectedVersion, expectedContent, content)`在同样的队列保护下整理AI完整正文；新版本沿用已有来源ID，不复制摘录，保留旧正文及全部active pending。相同正文不产生新版本，不提供借空正文清空画像的入口。仅本地可调用的`ConversationStore.reviewProfiles(plan, policy)`把多个人物、AI正文及已有`reclassifySelfProfileTerms`群规则迁移放在同一事务；任一步版本或权限核验失败则全部撤销。群规则迁移仍须来源群真实维护者权限，且只变pending投影的新版本也继承正文来源，避免当前版恢复核验丢失依据。不能借画像审阅扩大权限。暂时无法明确含义的个人pending继续保留，不伪造为已合并。

## 当前资料提案：单人物与独立组件（schema30）

新任务冻结`materialsProtocol=3`，固定拆成Topic、逐个人物、AI自身画像步骤。每步只处理自己的对象。Topic可以先保存；某个人物的提案、网络或版本冲突失败，不撤销已保存的Topic或其他人物结果。每个成功组件的实际数据和`auto_memory_component_results`记录在同一事务；进程重启和新恢复尝试依据成功记录跳过已完成组件。数据持久化损坏、失效租约仍停止工作，不能标成普通模型拒绝。根任务只有全部组件成功才done，否则保留failed、错误与原文，并按既有退避恢复未完成部分。

新捕获任务另冻结`profileProposalProtocol="delta-v1"`。人物增量提案示例：

```json
{"changes":[{"content":"喜欢简短回答","sources":["m0"]},{"content":"合并后的旧事实","replaces":["f1","f2"]}],"discardPending":[]}
```

`fN`来自当前唯一人物基线，`mN`只来自本步骤允许使用的真实来源。模型只提交新增、纠正、合并；`changes=[]`合法，程序原样继承所有未明确替换的旧事实。同一旧条目只能被一个变更消费，非法索引、重复替换和来源越界均拒绝。模型不再返回人物ID、版本、来源类型、事实数组下标、updates/evidence和pending处理映射。程序展开完整画像及这些关联，保留历史审计；纯基线合并保留补充确认来源，新事实更新按原时间和序号判断。`sources`也可引用`qN`，明确表示处理了哪条待办；仅引用原消息`mN`不会顺带归档同消息的其他建议。`discardPending`只指定确认不属于画像的待办，未使用的待办继续保留。

容量提炼沿用该标记，默认继承已经通过来源与对象检查的超限候选及其updates、pending结果，包括候选中新增加的事实。提炼的`replaces`只接受候选`cN`，不能混用原始基线`fN`；程序将合并后的更新关联映射回原始基线，完整结果仍须通过原来源、对象、时间、版本、容量和提交检查。候选不成为可信已归档画像或新权限来源。一次提炼机会与原共享预算不变。

未带`profileProposalProtocol`的旧冻结`materialsProtocol=3`输入继续使用`facts`的完整keep/replaces协议，遗漏旧事实仍拒绝；进度保存并核对新标记，不静默升级旧任务或混用进度。原文、旧版、冻结输入与失败证据保留。

新来源只包括当前房间目标本人真实发言、其pending原文，以及已授权第三方pending。同房间同人物的恢复复核资料也可作为新依据；跨房间旧画像依据只供继承、确认时间和复核，不扩大第三方权限或Topic范围。模型判断语句描述谁、是否属于稳定画像，程序不再用“我觉得”或有限亲属称谓黑名单判断语义。真实@与唯一人物名称绑定、连续真实原文和写入权限仍核验。语义判断可能出错，不能将来源有效等同于内容绝对正确。

模型返回的无关说明字段不参与写入；非法引用、实际越权对象、损坏JSON仍使对应组件失败。不能把被忽略的内容当成已保存。前台调用及新后台提取沿用真实身份和来源，当前画像仍只分已归档与未归档，不新增内部偏好分类。

渠道首次入库持久保存平台`mentionedSenderIds`，图像失败路径同样保存。schema30仅从已保存且事件ID、发送者、原文和房间route完全匹配的`channel_tasks.input_json`补回缺失真实@；已有记录不覆盖，无可验证事件时保持缺失。`message_profile_context_repairs`保存数量审计。用户自己输入`<@...>`文本不会产生权限。

以下旧复杂人物提案说明仍适用于未带`materialsProtocol=3`的历史冻结任务和离线审计；新恢复任务使用上述简化协议，不改写旧输入与旧失败证据。

## 人物、话题与原文

actor_id 保存某个人在某个房间的发言身份，person_id 汇总经过确认的同一人物。未绑定成员先使用独立人物记录，不按昵称合并。人物画像在绑定的群聊与私聊中共同使用，管理权限继续独立由 ownerBindings 决定。

`PA_DATA_DIR/policy.json` 保留原来的 primaryPerson，并允许多个 persons：

```json
{
  "version": 1,
  "ownerBindings": [],
  "persons": [
    {
      "id": "person_alice",
      "bindings": [
        {"route": {"channel": "qq", "accountId": "APP_ID", "roomType": "group", "roomId": "GROUP_OPENID"}, "senderId": "MEMBER_OPENID"},
        {"route": {"channel": "qq", "accountId": "APP_ID", "roomType": "private", "roomId": "USER_OPENID"}, "senderId": "USER_OPENID"}
      ]
    }
  ]
}
```

填写实际平台 ID；群成员 OpenID 和私聊 user_openid 不靠字符串相似度对应。绑定变更保留历史版本，已有独立人物归纳的事实及人物片段会随首次明确绑定合入目标人物，保留片段ID、正文、来源关联和旧画像修订，较新明确事实优先。

每次回答只直接读取当前发送者和本条问题真实 @ 对象的画像，重复对象去重。普通文本人名、历史 @、@全体和 @Bot 不增加人物候选。画像按上下文预算取用完整事实，不做人物向量或 FTS 检索。

群共享事实在请求中保留来源发言者 `sourceSpeaker`、来源时间、归属人物 `subjects` 和明确排除的 `excludedSubjects`；来源发言者不等于事实归属，昵称相同不合并人物。历史未分类记录只按原始来源补发言者，不猜测归属。全部有效明确归因纠正单列为 `attributionCorrections`，在同一10000字节背景预算内优先于画像、普通群事实与Topic完整载入；不以条数截断，也不跳过放不下的纠正，任一条放不下即明确失败，防止旧摘要或其他背景绕回已失效归因。当前prepare_turn实际保存的纠正通过完整回执供本轮回答使用；非空归因纠正回执超出工具预算会阻止回答，不返回截断JSON，也不回滚已提交的保存。普通无纠正回执沿用现有工具结果预算裁剪。

被有效纠正明确指向的旧消息，在模型可见的连续消息流中替换为中性占位并附 `correctedBy` 来源消息ID，SQLite原文及审计保持不变。来源涉及这些旧消息的Topic、人物画像事实及pending当轮不注入；纠正仍优先于旧会话摘要。历史流携带稳定personId，AI旧发言标记 `assistant_statement`，不能作为用户经历证据。read_history存储查询保留旧原文及correctedBy标记，前台工具投影同样替换为中性占位。纠正查询及映射限制在当前房间和本轮可见边界内，不扩大画像候选、身份共享、owner权限或工具预算。

纠正链沿历史归属修订保留失效来源：再次纠正一条纠正时，也继续屏蔽它所否定的更旧说法；纠正记录过期不会恢复旧错误为有效证据。当前有效纠正正文与历史失效定位分别投影，原始消息、旧记忆及各版归属元数据仍保留。显式引用能够定位到已纠正的原始消息时，同样只注入中性占位与纠正来源，不扩大引用读取范围。

若纠正所否定的来源已在当前可用压缩摘要的检查点之前，则当轮摘要投影置空，并提供 `summaryUnavailableReason`，明确要求使用本轮有效资料或历史核验；包括纠正正文已经过期的情况，避免旧归因仅凭压缩摘要重新进入模型。数据库原摘要及检查点保持不变，不自动回退或改写原文。

已有 `/memory correct` 对带归属记录进行同正文的时间等元数据修订时，保留归属元数据；若要改写带明确人物归属或纠正标记的正文，必须通过新的结构化归因纠正，不允许旧无结构修订接口丢失或猜测归属。失败会保留原记录及修订，不回执成功。

群聊与私聊统一提供固定压缩摘要和检查点后的完整消息流，不限制最近10条或10分钟。真人消息在入站时可见，Bot回复只在确认送达后可见；晚送达回复追加在尾部，不回插旧历史。每轮固定当前问题入站时的可见边界，排除本轮、之后到达的消息、控制消息和其他房间。保留原发送者与回复对象，不扩展当前画像候选，不执行历史中的保存要求。历史、摘要与Topic均是对话资料，可能无关或过时；当前身份、服务器时间和保存回执分别只确认身份/权限、时钟和操作状态。

新 Topic 保存有价值的讨论摘要，程序记录所属任务及生成步骤的固定来源区间，不要求模型枚举每条原文。区间只表示生成背景，不证明区间内每条消息支持摘要；旧 Topic 的精确来源关联及人物片段继续保留。画像是当前已归纳状态，仍保留少量精确真人证据。Topic仅按来源房间使用中文FTS5/BM25检索，不做向量匹配。原文按房间保存，人物画像共享不复制其他房间全部历史。

## 后台整理与并发

- 对话压缩与画像/Topic资料整理独立调度。压缩只按完整上下文容量触发，不按50条消息或50轮问答；资料整理检测到新真人chat或新增画像pending才开始计时，空闲10分钟或本轮累计30分钟先到触发一次。一次触发同时清空两个计时；没有新增内容不启动新计时。两个时间保存在SQLite中，重启后恢复，不用“服务启动时间”重新计算。
- 最终请求占用含输出预留达到实际窗口85%时触发；不硬编码1M，也不把本次容量快照再截成50条。前台使用成功SDK输入用量校准，相同历史沿用实测值，新增内容仍按字节保守计量；输出、准备/工具结果和安全余量另行保留。无适配样本时使用UTF-8字节备用估算，不把它当实测token。
- 固定原文成员、待处理pending与任务状态后再请求模型。新消息立即入库；任务预约后新内容进入下一轮计时，旧任务完成不得清掉新一轮。重复轮询、重复渠道事件、控制消息、AI回复本身不启动或刷新资料计时。两条流水线分别按序，可以独立运行；资料任务失败或等待模型时不堵压缩，前台只等待压缩完成。调用次数预算仍共享。
- 新滚动快照标记 `extractionProtocol=2`，程序记录步骤处理范围，不再要求 `ignoredMessageIds` 或真人消息逐条语义覆盖，也不新建人物事件片段。模型处理完一段范围不代表程序证明了它理解每句话；原文仍可独立查询。
- 新资料按上述schema30组件分别原子保存Topic、画像修订与pending回执，全组件完成才推进根任务覆盖；不修改续聊摘要或压缩水位。压缩成功只原子切换摘要和压缩水位，不修改Topic/画像。失败保留固定批次和诊断，当前materials/compression登记有界恢复新任务，旧租约不能提交；旧冻结协议不通过改写版本重新执行。
- 请求前同时检查输入容量和预计输出预算：能放下时仍可一次处理；需要时拆成顺序消息摘要、完整人物画像或AI pending步骤，保存成功进度，完整旧画像不按预算裁成局部输入。消息摘要和Topic正文有独立篇幅预算；输出估算仅作风险控制，实际截断仍失败，不自动追加收费调用。
- 新资料快照标记 `profileBaselineProtocol=1`：模型以完整当前画像为已归档基线，只接收本批新增聊天和捕获pending所需的原文；不再重复发送已归档画像的旧依据正文或历史profileFragments。旧事实的来源类型、时间及局部来源引用继续传递，允许继承、合并精简；新增与纠正仍核对本批真人/pending来源，不得跨人物或将推断升级为自述。pending的superseded必须引用本次实际可见的更新本人来源，不能依赖未展示的旧依据。
- 来源原文、旧版本和关联不删除；内部冻结输入仍保留证据用于身份绑定变化、来源强度、旧协议和提交校验及离线审计。原始来源与模型投影分别管理，不把完整冻结输入直接发送模型。新标记随步骤检查点保存并与固定输入核对；无标记的旧冻结任务和进度继续原投影，不在恢复时静默切换协议。当前用户/AI画像的容量、权限及10/30分钟和85%触发边界保持原规则。
- 请求超过硬上限时，等待相关批次完成后重新构造请求；等待有截止时间。无可压缩历史或当前输入仍过长时返回失败，不发送超限请求。
- 群聊与私聊都使用最近成功的continuationSummary和检查点后的完整消息流。新摘要承接旧摘要与固定快照中的新增对话；仅成功后原子切换，失败继续保留旧摘要和原文。Topic继续按房间FTS5/BM25检索；会话压缩摘要不作为独立群情报摘要。
- 每秒巡检观察新内容、检查10/30分钟计时及可执行队列，不是每秒调用模型。没有新资料不空转调用。未开始的排队任务可在启动和巡检时继续，不要求先收到新消息。关闭取消在途调用；materials/compression失败和过期租约进入下述持久恢复流程；旧legacy隔离任务不自动复活。
- 本地操作者可显式搁置失败批次，保持原 `failed` 行、冻结输入、进度、错误和固定成员不变；旁表记录原因、时间及输入/进度哈希。当前materials/compression失败会登记恢复并退出执行队列，后续仍可领取；legacy旧协议保留原显式维护语义。状态分别显示 `failed`（仍阻塞）和 `deferred`（已搁置）。搁置不是完成：连续水位不跨缺口，缺口原文仍保留，会话摘要与后台输入用 `deferredRanges` 明示未覆盖区间。搁置批次禁止普通 retry 和迟到提交，避免旧画像或摘要覆盖新状态；当前两条流水线的补录使用新的恢复快照，不能直接改版本重放旧结果。
- 旧count协议的遗留队列可显式退役后交新容量协议接管：仅首次滚动快照前、无运行任务和租约时允许。退役保留旧任务及已有搁置审计，单独记录原因和哈希，不等于完成，也不请求模型。旧原文继续出现在上下文，并可完整纳入下一次85%容量快照；不再把这些原文永久排除为deferred缺口。状态另报retired，原始status仍供审计。普通失败/搁置逻辑不变。

模型提案经过结构和来源检查；画像更新使用版本 CAS，旧批次不能覆盖较新自述。人物画像协议 v2 提供完整人物画像并返回完整替换结果，不再裁掉旧事实后自动补回；必要时在同一固定批次内按消息、人物或 pending 分块，进度持久保存。完整人物画像及必要来源本身放不下时明确失败，不把局部视图冒充完整画像，不自动调用模型修复。

### 按实际用量校准上下文

Pi已将缓存输入从 `usage.input` 分出，所以实际输入合计为 `input + cacheRead + cacheWrite`；`output`及其中的reasoning不再加入输入。只学习每次实际请求对应的完整成功响应，拒绝缺失/全零、负数、分数、不一致计数和失败/中断响应。SDK未报告usage时默认全零，不能把它解释成实际零占用。后台提取的独立输入预检仍使用原有保守估算。

校准按供应商、接口、模型和稳定房间标识的哈希隔离。新版指纹细分实际请求中的字段、正文及嵌套JSON历史行，按哈希和重复次数匹配；给旧消息补personId、sourceType等字段或调整键顺序，不再使整段正文指纹全部漂移。所有字段、序列化与转义开销仍计入总字节，新增或变化内容按字节全额估算，不将旧中文密度直接套到新代码等内容。只有至少保留样本90%字节时才沿用完整实测输入，不因少量删除按比例扣减；换摘要、大幅正文变化或旧图片缺失时回到安全估算，下一次成功usage再建立基准。

指纹随调用记录保存在已有诊断索引中，只含哈希、长度、次数和有界结构元数据，不保存原文。查询先按同一校准绑定及成功状态过滤，再从最近100次相关调用中恢复最多8个有效样本，避免繁忙房间挤掉其他房间的基准。旧v1记录继续可读；仅在没有新版样本时，最多读取8个旧成功请求且累计不超过16MiB，先核对工件哈希，再验证其完整旧指纹与原样本一致，才在内存中生成新版指纹。正文已脱敏、缺失或校验不一致时不升级，保留旧匹配和安全估算；原记录不改写。有新版样本后直接恢复指纹，不重复读取旧请求。重启、独立渠道task会话仍可复用同房间样本，不新增业务库schema或依赖。旧记录缺少接口绑定时不追溯混用。准备阶段成功usage立即用于本轮后续工具循环；前置85%和含工具结果的实际请求硬上限使用同一校准方式。

这仍是事前估算，无法在请求发送前取得它的真实usage；新文本和输出预留、安全余量可能使整理略早发生。当前按包含messages数组的请求载荷匹配，已验证DeepSeek/OpenAI兼容接口；其他载荷形状继续使用备用估算。不会为了测token另发模型请求，也不取消硬上限或自动重试未知结果。

### 人物画像容量与 pending 生命周期

当前生效人物画像同时限制为80条事实、每条120个Unicode码点、正文合计8000个UTF-8字节，以及 `{personId,baseVersion,facts}` 完整结构16000字节；不再设置每条事实的来源数量指标。群聊与私聊共用人物画像，均使用此规则。正文通常每条20至50字符，不为用满容量扩写。内部来源关联继续用于发言者归属、证据强度、纠正和pending校验，不截掉合法来源或放宽身份边界。正文及结构是字节上限，不是token预算，也不包括独立限量的active pending。达到60条、6000字节正文或12000字节结构时，下一次既有后台批次必须给出完整收敛结果；不单独因75%阈值发起模型调用。单个人物步骤还会按实际输出token预算给出更小的收敛目标，始终发送完整基线，不通过裁掉输入绕开预算。新版本在去重合并后和事务写入时均校验硬上限，不静默截断，不无限并回未展示旧条目。历史已超限的旧版本不在迁移中裁剪，后续完整整理成功后才切换当前版本。

模型依据真人来源合并同义事实、处理较新明确纠正、精简表达，避免把临时事件或一次评价固定为人格。达到软线时尽量收敛到软线以下；程序不能判定语义等价或保证模型提炼质量。安全校验不通过时保留原画像及原文。完整历史仍保留，不新增人物历史检索或个人长期事件模块。当前每轮载入预算继续独立生效，并非每轮必须载入全部80条。

新资料任务仅在整步结构、人物对象、来源和全部pending结果校验通过后，才判断是否需要容量提炼。完整但超限的结果先存入检查点；每个步骤中的每位超限人物最多增加一次 `mode=profiles` 专用提炼调用，复用共享预算、超时和诊断。原 `profiles` 仍是可信基线，超限草稿仅放在独立 `profileRefinement.candidate` 中；基线索引、证据与权限校验不变。提炼调用前持久化 attempted，成功后持久化修正结果；重启/显式重排不重复已完成的提取、Topic或提炼，也不自动重发未知结果。预算不足时保留尚未发送的提炼阶段，仍按预算规则暂停。

若专用提炼仍超限、输入输出预检无法容纳，或已收到的提炼响应明确截断/无效，保留现场并在同一租约事务中记录失败及自动搁置，让后续资料批次继续。请求超时或结果未知保留失败尝试，不接收其迟到结果；按下述新恢复任务与持久预算处理。

新materials模型提案明确发生JSON、结构、画像对象或证据拒绝时，也可原子记录失败并搁置，后续资料批次继续。这个范围只包裹新响应及纯模型提案校验；本步骤profiles才是可写对象，profileSubjects仅用于身份辨认，普通问句不能推断为本人已经使用某物。输入/旧检查点协议、版本或身份绑定变化、取消/未知请求等错误保留失败现场，由新快照有界恢复；数据库及诊断持久化故障仍停止工作器，不能假装已记录并继续。

搁置不等于成功：旧整批提交协议被拒绝时不写该批画像/Topic；新schema30保留已成功组件，只让失败组件及其pending等待补齐，根任务未完成不推进连续覆盖。旧版本、原始消息、冻结输入、成功记录及哈希均保留，资料任务均不推进压缩水位。后续完成的批次不抹去缺口，当前materials/compression会登记独立、有界的自动恢复任务。普通重试与迟到提交不能恢复已搁置任务；旧failed行不改写为成功，旧legacy隔离记录仍需显式维护。自动恢复消耗既有模型预算。

每条已捕获的待整理资料必须有明确处理结果：`merged` 指向新画像中的事实，`superseded` 指向更新且属于本人的保留依据，`not_profile` 标明临时信息/非个人资料/证据不足，`deferred` 继续等待。新增、跨人物、已被处理或内容变化的pending不得借旧快照处理；本人自述不能被更晚的第三方说法直接覆盖。

成功事务同时写入新画像版本、`person_profile_pending_results`无正文回执和`person_profile_revision_sources`来源关联，然后物理移除非deferred的active pending。这样释放待整理名额和正文额度；deferred继续保留正文，旧已归档pending不批量清理。原始聊天、旧画像版本、冻结输入和诊断证据仍保留，因此不承诺SQLite文件会立即缩小；这只是内部成功队列的清理，不开放用户删除画像/原文的命令。

新固定输入标记 `profileProtocol=2`，分块检查点使用独立版本。旧冻结输入或旧检查点不会被静默改写成完整替换协议；升级前未完成混合任务保留原状态、快照与进度并隔离，纯离线诊断仍可解析旧格式。新流水线尚未捕获输入的排队任务首次执行时使用当前协议。

## 失败恢复与时间顺序（schema29）

失败尝试、原始消息和恢复任务分别保存。`auto_memory_recoveries`记录失败根任务、恢复次数、下次可运行时间及替代任务ID；旧failed/input/progress保留，旧租约不能迟到提交。后台巡检先登记materials/compression的未跟踪失败，再预约到期恢复；恢复使用新任务、新基线和新调用，不把旧错误结果伪装成成功。

每个失败链最多自动恢复3次，依次等待1分钟、5分钟、30分钟，次数与到期时间写入SQLite，重启不重置。恢复仍受既有后台调用预算限制。耗尽后保留可查询的未覆盖缺口，不反复每秒请求；其他独立任务继续。真实存储/诊断故障停止工作器。研究、QQ未知投递和旧legacy隔离任务不适用这项自动恢复规则。

同一压缩快照耗尽后，不能靠重复容量信号重置次数；后续确有新增原文并再次触发容量压缩时，可以建立包含旧缺口的新快照。后台预算用完则暂停领取，不把尚未调用的排队任务都记为失败。失败恢复仍暂缓的画像pending会随归属转移，在恢复任务成功后可被下一轮继续领取。

**压缩**从上一次成功的`continuationSummary`和压缩水位重新取完整后缀，按持久可见`contextSeq`排序，包含失败原文以及后续聊天，不再过滤被搁置的压缩成员。仅成功提交才原子切换摘要和水位；失败保留原摘要和全部未压缩原文。若恢复仍失败且输入超过模型硬上限，当前会话无法继续向模型发送完整上下文，不能通过跳过原文绕开容量限制。

**资料整理**恢复失败成员，按原始消息顺序处理，领取时重新捕获当前可信画像。用于判断先后的后续原文和跨房间同人基线来源作为只读复核资料；这不扩大人物写入权限或Topic房间范围。覆盖进度依据成功任务的实际成员计算，不能仅取最大任务结束序号来跨过中间缺口。

执行时间不等于事实时间：10点“喜欢咖啡”失败，11点“现在戒咖啡”成功，12点补做时，10点那句话仍保留原始时间与来源序号。程序阻止仅以较旧依据删改较新基线；无关的旧事实（例如“喜欢猫”）仍允许补入。AI画像的旧依据也不能整体替换较新的完整设定。模型需要根据原文判断语义关系，程序不能保证识别任意措辞的矛盾，不能把时间校验宣传为通用语义判断。

人物事实的补充确认来源也参与新旧比较，即使正文与主来源未改变；时间相同则用原始入库序号比较。只读复核资料不变成新写入依据。冻结JSON或检查点损坏须先排查存储，不能依靠新尝试掩盖损坏。

失败恢复不会把原文重新插到聊天末尾，也不因恢复调度改写正常对话历史。成功压缩替换摘要会改变该位置之后的缓存前缀，之后再围绕新摘要增量积累；缓存命中不作为记忆完整性的依据。

本地操作者可以查看状态，或为最新失败尝试明确授权额外一次恢复（服务开启时会消耗模型预算）：

```powershell
node --env-file-if-exists=.env dist/memory-jobs-cli.js status
node --env-file-if-exists=.env dist/memory-jobs-cli.js recover FAILED_JOB_ID "故障原因已修复，授权补齐一次"
```

`jobs[].recovery`显示根任务、次数、到期时间、替代任务ID及是否耗尽。`recover`保留人工原因，不把已耗尽的自动次数清零，也不重放旧结果；真正的持久状态损坏不接受此命令。

## 启用及预算

在已有 `.env` 中按 `.env.example` 补充：

```dotenv
PA_MEMORY_ENABLED=true
PA_MEMORY_MAX_CALLS=20
PA_MEMORY_TIMEOUT_MS=120000
PA_MEMORY_MAX_OUTPUT_TOKENS=8192
```

启用会增加调用费用。后台复用聊天provider/model，独立会话、输出预算和超时；所有房间共用PA_MEMORY_MAX_CALLS，0表示不限次数。失败请求及画像容量提炼计数，超限拆分的本地预检不计实际请求。SDK重试关闭；除上述对完整超限提案的一次专用提炼外，不自动补发失败/未知调用；已取消未生效的PA_MEMORY_MAX_RETRIES。

Topic仅按当前房间用中文分词FTS5/BM25读取，状态为lexical，每个Topic最多携带5条与其自身来源相连的事实，不读取其他房间证据。向量配置、Embedding接口、预算、派发与相似度/RRF运行逻辑已移除；旧向量表与attempt原样保留，不读取、不重新派发。

## 显式更新与管理

### 历史资料回填

本地操作者可以显式回填旧隔离范围或尚未整理的历史。先停止服务并备份完整数据及配置，再执行；`reserve`生成普通材料队列，运行中的后台可能立即领取。schema22只增加回填审计及backfill任务类型，旧任务原行、冻结输入、错误和已有进度保留。

```bash
node dist/memory-backfill-cli.js plan CONVERSATION_ID
node dist/memory-backfill-cli.js reserve CONVERSATION_ID "明确的维护原因"
node dist/memory-backfill-cli.js status RUN_ID
# 此命令才执行收费模型；复用现有provider/key，不连接QQ，不开启自动计时。
node --env-file=/etc/pa/pa.env dist/memory-backfill-cli.js run RUN_ID --max-calls 128
```

计划和查询不需要模型凭证。一次预约冻结当前可见截止和有效pending，默认每批最多100条消息、65536字节消息结构；pending另按最多20条拆批。单条超大消息独立成批，再由真实输入/输出预检决定能否执行。已完成旧任务的实际成员、所有已被材料任务预约的消息及待办不会重复预约。画像基线在各批领取时读取，避免后批带着同一旧版本覆盖前批结果。

每个run单独保存计划哈希、批次和旧pending状态审计。新消息走下一轮正常计时；回填不推进对话压缩水位。执行只领取该run的任务，不越过该房间材料队列的前序。普通失败停止并保留进度，不自动重试；仅上述画像容量提炼耗尽时可原子搁置并继续范围内后续任务。日志按jobId/callId排查，显式处理后可继续未完成步骤。`remainingPending`表示尚未成功执行批次的待办数量，`retainedPending`另外显示仍保留的未归档/暂缓条目，不能将它们冒充已归档。重跑已完成run不调用模型。

回填CLI显式启用分步计划：消息Topic、逐人物完整画像、AI画像分别请求。计划在首次调用前持久化，成功步骤保存进度；已有检查点按原计划恢复，不因配置变化重排。人物步骤不发送AI消息，仍保留完整画像和相关真人依据，来源数量、身份、版本及pending校验不放宽。普通自动整理不因这个维护选项改变执行计划。已失败的旧合并步骤若需改计划，必须由操作者保留原输入、进度和响应审计后显式处理；已有进度不静默重解释。

4096 tokens的聊天回复上限不限制待整理原文总量。后台输出预算和模型输入窗口独立；输入或预计输出超限时在请求前拆步骤，真实响应截断、格式错误或调用结果未知则保留失败现场，不自动补发收费请求。原文和旧版本不因分批而删除。

### AI 自身画像

AI 自身使用一份跨场景的全局画像，和用户画像分开。SQLite 保存“已整理画像”和“待整理补充”，不维护第二份可写的画像文件，也不增加针对某个人的相处模式。

允许接入场景中的任何成员都可以提出明确补充，无需管理者身份。群聊仍须真实 @ 机器人，私聊遵守已有白名单。例如：

```text
请记住你的名字叫初号机
你记住一下，你以后回复不要太正式
你记一下以后回复简洁一点
以后你的回答简洁一些
/self 解释复杂问题时先给一个直观例子
```

渠道自然语言统一进入同一 Pi Agent Loop 的强制准备阶段：第一请求只开放 prepare_turn，返回 intent、mode、updates。没有持续保存意图时 updates=[]；不以程序匹配“记住”前缀代替模型理解。每轮最多8项、总共20000字节，content必须连续摘录当前消息；个人每条最多4000字符，AI每条最多500字符。harness逐项验证身份、范围和容量，在同一SQLite事务提交全部更新与来源消息级幂等回执，再请求正式回答。任何一项越权则全部回滚，不能部分确认。保存成功与回答/投递成功分别记录，回答失败不会擦除已经提交的资料。

prepare_turn 的 target 可为 sender、mentioned_person、ai_self、room_rule、room_memory。普通成员仍只能保存本人资料和建议AI全局画像；mentioned_person仅管理者可用于当前消息明确指向的已知成员，并固定为third_party证据。群规则和群共享事实仅管理者可写，且仅当前群有效。sender/mentioned_person仅用于稳定画像；不再提供purpose字段或个人事件保存。个人经历、一次性计划不因取消模块而改存为画像或群记忆。

发言者与画像对象分别校验。发言者取原始消息的实际actor/person绑定，模型只能给出当前原文中的对象依据：`subjectKind=self/mention/name/ai` 与 `subjectQuote`。harness用本人明确自述、平台记录的真实@或当前房间唯一已知身份确认对象，不把消息来源ID当作对象ID。例如A说“B不吃辣”，不能写入A的画像；只有管理者明确更新B且对象可确认，才能保存B的third_party pending，发言者仍记录为A。普通成员不能因此获得修改B的权限。引语中的“我”、“我朋友不吃辣”、假设、转述及对象不明确的输入保守拒绝保存，仍可继续正常对话；这些校验不能保证识别所有自然语言歧义。

准备后回答阶段关闭画像写入和旧的深度切换工具，mode=casual/standard/professional只选择表达提示，不改变权限。普通请求至少2次模型调用（准备、回答），均计入原有每轮6次预算；历史与网络工具续轮额外占用同一预算。准备阶段目前验证了OpenAI兼容协议，其它供应商协议未接通时请求前明确拒绝，不退回不受约束的保存。模型忽略强制准备、并列其它工具、无保存回执却作出明确保存宣称时阻止发送；这不等于已验证模型对所有自然语言意图都能正确分类。

个人与AI画像均只分已归档和未归档。新画像建议先保存在pending，下一轮连同归档画像注入；个人事件模块已停用。旧purpose=memory pending及个人memories保留，不注入、不查询、不纠正、不转成画像。已冻结输入或进度若包含旧个人事件协议，会明确失败并保留原JSON，等待操作者处理；普通重排不会暗中改写旧协议。画像只用于措辞、例子、偏好与风格的软参考，不作为回复提纲反复复述，不暴露内部标签或提供普通成员的画像导出。旧审计分类元数据保留，但不会要求模型继续输出。

每轮提供当前发送者与真实@对象的身份卡，即使暂无画像也保留身份；显示名与稳定person_id分开，维护者身份按当前平台账号及房间的ownerBindings验证，人物合并不授予权限。

### 群规则与术语

“本群pa代表personal agent”保存为本群规则，而不是人物或AI画像。room_rule_revisions按群、规范化key、revision保留原文和来源，纠正生成新版本；仅当前群注入，不能改变身份绑定、权限、工具白名单或预算。规则最多50项、当前版本总计12000字节。不同群独立；私聊不创建群规则或个人事件记忆。

历史误分类通过明确的本地维护计划迁移，不用模型批量猜测：reclassifySelfProfileTerms核对pending ID、预期原文、原群及ownerBindings，追加群规则和画像投影修订，并在self_profile_reclassifications关联前后版本。旧原文、pending和修订不删除，活跃画像及其容量计算排除已迁移条目。已有归档、目标规则冲突或来源无群管理权限时拒绝，不能借迁移把普通成员或私聊建议提升为群规则。该操作不是聊天/模型工具，也不改变任何权限配置。已有后台输入快照保留，旧提取结果不能将已迁移来源重新写回AI画像。

历史由read_history工具按当前房间和发言者过滤，使用中文分词后的SQLite FTS5/BM25检索；没有关键词时可按时间读取最近记录。默认当前发送者，群内可查询本群其他成员；每次最多10条，包括对应问答补充。已整理原文仍可查询，不扩展人物FTS或向量检索。完整流程、提示词结构与循环限制见[工具循环流程图](design/companion-tool-loop.md)。

独立资料整理任务合并自我画像建议，无需等到85%压缩。不强制每批形成新性格；无新依据时保留旧内容。已处理条目标记归档，保留原文、来源和修订；仅归档预约快照中明确处理的ID，在途新增继续待整理并独立计时。跨房间同时更新使用全局版本检查，旧结果不得覆盖新版本。AI自己生成的发言不能单独作为自身事实证据。

AI当前画像快照使用 `protocol=2`：只带正文、版本及当前pending，不再累计历史来源ID，也不再有500个累计来源的限制。每次修改的原文摘录保存在 `self_profile_updates` / `self_profile_update_sources`；处理pending时同事务保存关联，即使正文未变也保留处理审计。历史修订及其旧来源数组不改写，迁移时额外记为 `legacy_snapshot`，不伪造历史逐次修改。跨房间版本冲突、来源已迁入群规则或原文与捕获pending不一致时拒绝提交。

AI正文仍最多4000字符，每条建议最多500字符，待整理正文最多12000字节、100条；当前完整快照受实际上下文窗口15%（最多20000字节）的预算限制，历史审计不再占用当前快照。超过容量会明确拒绝本次保存，不回执“已记住”；可等待整理或缩短建议后重试。固定系统规则、权限、工具与预算仍由程序和本地配置决定，不能由画像修改。

普通成员可提出本人画像补充或AI全局画像建议，由模型调用工具保存，不获得管理其他人物、导出全部档案或改变身份绑定的权限。保存不要求用户选择分类。

管理者保留 `/memory remember room 内容`、`/memory query`、`/memory correct ID 内容`。这些显式管理指令由程序鉴权并执行，成功短确认；查询结果、权限拒绝、澄清、报错和命令帮助直接返回。离线 CLI 保留 remember/query/correct，仍不调用模型。管理查询仅覆盖当前会话群共享记录；me/user个人目标和旧个人记录ID均拒绝，人物画像通过自然语言更新，不导出普通成员画像。QQ私聊不创建、查询或纠正房间记忆；CLI离线房间管理保留用于验证。需要群记忆ID时通过管理查询获取。

```powershell
npm start -- memory remember --conversation owner --content '本群pa代表personal agent'
npm start -- memory query --conversation owner --query 'pa'
npm start -- memory correct --conversation owner --id ID --content '本群pa统一指personal agent'
```

不提供 delete、/forget 或自然语言删除；旧命令本地拒绝，不擦除记录。平台撤回也不删除已保存原文。纠正保存修订并更新当前值；数据库记录“某人曾说过什么”，不把所有陈述自动视为已证实事实。

后台诊断与重试无需模型密钥：

```powershell
node --env-file-if-exists=.env dist/memory-jobs-cli.js status
node --env-file-if-exists=.env dist/memory-jobs-cli.js retry JOB_ID
# 先暂停后台并确认运行进程已加载PA_MEMORY_ENABLED=false，再搁置：
node --env-file-if-exists=.env dist/memory-jobs-cli.js defer JOB_ID "保留失败批次，等待单独补录"
```

retry 只重新排队，启用后台记忆的服务在巡检或下次启动时执行，因此人工重试会再次调用模型。失败、进程中断或租约过期不自动重试未知结果的收费请求；原文、固定批次、已成功子批进度保留，后续同房间批次保持顺序。状态输出含任务ID、状态、阶段和经过白名单筛选的错误类别，不包含供应商原始错误、原文、画像或密钥。QQ服务状态显示任务数量与共享调用次数。

`defer` 本身不调用模型，但在运行中的服务启用后台时，会使后续批次恢复收费调用资格。禁止收费联调时，先停止服务、备份数据及配置，将 `PA_MEMORY_ENABLED=false` 并重启确认生效，再执行搁置。保持后台暂停可验证领取资格与数据保留；后续批次尚未实际整理，不能称为已清空积压。恢复后台需明确允许费用。

从旧50条/50轮协议切换，且本会话尚无任何滚动容量快照时，可先停服务并备份完整数据，再执行：

```powershell
node --env-file-if-exists=.env dist/memory-jobs-cli.js retire-count CONVERSATION_ID "旧计数任务退出执行，原文交85%滚动容量压缩"
```

命令只退出该会话尚未完成的旧count任务，保留其原始queued/failed状态、旧deferral、固定成员、输入/进度和错误；不把它们伪造为done。已退役任务不能普通retry，重复维护不会重写审计。若已有rolling快照或运行租约，整批拒绝，避免改变在途快照覆盖范围。服务恢复后等待真实85%条件，命令本身不强制提前整理。

提取先读固定原文批次与已有事实，产出少量 Topic、续聊摘要及必要的稳定画像修订。新模型请求只用绑定本次输入的短引用（消息m、人物p、人物pending q、AI pending s），返回后按字段映射回数据库ID，再检查身份、证据和版本。Topic不返回逐条来源；程序用固定快照中的ordinal区间追溯，不按稀疏的原始ingestSeq猜成员。区间触及已纠正的旧消息时保守跳过该Topic，且不因处于同一区间就附加人物事实。人物画像不再限制单条来源数量，pending完整审计另存。事件与讨论不自动转为人格。

新资料任务冻结 `profileAttributionProtocol=1`、`selfProfileProtocol=2` 和本批身份字典。通用旧协议的模型提案使用 `updates`，包含事实索引、可继承基线索引和原文对象依据；当前单人物最小提案只提交事实与来源引用，由程序绑定身份和生成关联，不要求模型重复摘录。提取验证和最终落库检查来源、目标和版本；只能引用本步骤新增聊天或捕获pending所需来源，不能从旧依据里提炼新事实。原样保留的事实无需重复举证，同一对象的基线可显式合并；新third_party依据必须对应已授权pending中的对象定位，不能靠后台自动提取绕过前台权限。分步整理把中间索引还原到固定初始基线；成功后 `person_profile_subject_updates` 仅新增来源/对象类型元数据及实际发言者与画像对象关联，不复制原文摘录，旧记录原样保留。范围/身份校验通过不等于陈述内容已经证实。

`mode=messages` 的输出模板明确要求 `profiles:[]`。如果正常结束的合法JSON仅省略此恒空字段，解析层可确定性补为空数组；显式null、错误类型、非空画像、未知字段和其他模式缺少必需字段仍拒绝。此兼容不补造模型内容、不放松JSON语法或结束状态，不增加模型调用或自动重试；诊断继续保留原始响应，可按原冻结步骤输入离线重放。

旧冻结输入缺少 `extractionProtocol` 时继续按旧结构解析；其原输入、旧进度和响应不自动升级。新进度为version 3，记录少量步骤完成区间；旧进度version 2保持原协议。日志离线重放按保存的协议还原短引用，不调用模型、不提交业务库。详细取舍见[整理协议v2设计](design/memory_consolidation_v2.md)。

缺少本次画像协议标记的旧资料任务，在请求模型前停止，也不能普通retry或提交迟到结果；原始任务、冻结输入、成功步骤和错误继续保留，等待显式维护。离线旧协议解析保留用于诊断，不构成现场执行权限；不自动升级、重排或补发收费请求。独立对话压缩不受此画像协议切换影响。

## 迁移与验证范围

schema v23首次打开旧库时用VACUUM INTO创建同目录 `.v旧版本.UUID.bak` 一致性备份，再事务迁移。v11增加准备回执、群规则修订、个人pending用途与Topic全文索引；v12增加旧AI画像条目迁入群规则的版本关联审计；v13新增失败任务搁置旁表；v14新增人物pending处理回执及版本来源关联；v15新增可见消息顺序、滚动摘要状态与完整容量快照；v16新增旧count任务的显式退役审计，不重写旧画像正文；v17增加长回答完整正文文档、页面投递与引用索引，当前仅保留旧分页数据供历史读取与引用解析；v19增加共享事实人物归属及纠正旁表；v20新增 `memory_topic_scopes`，每个新Topic保存两个快照ordinal；v21保留任务rowid和原字段，增加两条流水线、独立资料计时/进度及固定成员/pending捕获表，旧未完成混合任务由旁表隔离并保存输入/进度哈希，不改原状态、不自动重试；v22新增显式回填计划、批次与pending状态审计，授权后以新材料任务处理指定历史；v23增加人物pending的subject_json、真实提及消息元数据、人物对象更新审计及AI画像独立更新/来源表，迁移保留所有旧修订与冻结任务。旧成功资料只按实际成员确认覆盖，旧未完成范围不冒充已整理。新QQ回答用原生Markdown自动分段并将完整投递正文存为快照。保留已有消息、绑定、画像、失败快照和整理水位，删除墓碑不自动恢复。迁移回填已有Topic索引及可见历史，但不全量付费提炼旧历史。当前会话确因历史超容量时，容量任务才捕获固定边界的全部增量；前置容量估算同时预留动态准备提示的空间，发送前继续检查完整请求的硬上限。

## 图片与续聊压缩

资料整理在同一数据库内逐任务串行领取、捕获画像快照并提交，避免同一人在多个房间的任务同时基于旧画像版本执行。进程内等待队列公平让出，关闭工作器可取消等待；数据库领取同时检查其他工作器的有效资料租约。压缩流水线继续独立执行。版本检查仍保留，未知或已失效调用不会自动重跑。

压缩固定输入额外包含程序确认的共享事实纠正链、纠正原文、被纠正原文及人物归属，使旧摘要中的错误也能被修正。提交时在同一事务保存该输入实际包含的纠正指纹；后续读取仅在有未覆盖的纠正影响摘要范围时隐藏摘要。整理过程中新增或迟到的纠正不会被旧快照冒充覆盖；无指纹的旧冻结任务也不能宣称已经处理纠正。原始消息保持不变。

同一continuationSummary周期内，消息携带图片metadata及真实file块，按原消息位置持续追加，不滑窗删图、不每轮重描述、不修改旧图片URL。引用内容保留quoted及来源发送者，不能认作当前发送者自述。同图已在未压缩消息流里时不重复加载；未知原消息引用图保存为当前提问的附件并关联引用哈希。非@图片和纯图片会保存，但不主动调用聊天模型。

85%阈值包含每图1024 tokens的保守预留；usage指纹保存哈希后的图片身份，新增图片仍加足预留，图片更换/移除不能借旧图片实测额度打折。600张或200MiB图片API硬限制单独检查，超限复用capacity压缩，不当作文字token或静默丢图。后台固定输入保存稳定imageId/fileId，处理消息时模型实际收到图像：压缩将相关视觉信息和可回查imageId写入continuationSummary，资料整理只在有价值时写入Topic；画像专用整理不额外注图。单个固定任务超输入容量时按现有子批次机制拆分，完整原文和原图仍保留。

成功切换摘要后，不自动重新注入旧图；当前房间的read_history返回稳定图片metadata供定位，read_image可把原图作为真实user file块追加到当前工具结果组尾部。read_image不能读取路径、URL或跨房间图片。当前模型账号没有已存文件映射时明确失败，不发送旧账号句柄。原图不会因为摘要完成而删除。

read_image和其它工具读取采用相同范围：原图仅追加本次工具循环，后续轮如有需要再次读取，复用已保存Files句柄，不重复上传，不回填或改写已公开的消息历史前缀。用户引用/直接发送的图片附件才会随当前压缩周期的原消息持续注入。附件下载/上传失败仍保存原始问题与无URL的失败回执；同事件重投直接去重，不自动重试未知上传，历史明确附件未读取成功。
